# 测试与诊断

[返回首页](../README.md) · [开发指南](开发指南.md) · [SDK AT](AT指令.md)

这份文档讲两件事：改完代码怎么测，出了问题怎么判断是哪一层的问题。

## 测试分几层

能在低层证明的问题，不要留到高层；真人只确认机器判断不了的东西，比如听感。

| 层 | 测什么 | 怎么跑 | 要多久 |
| --- | --- | --- | --- |
| 静态检查 | 目录结构、依赖关系、产品契约、改动影响 | `python scripts/check_structure.py` | 几十秒 |
| 主机测试 | 各模块的输入输出、失败路径、故障注入，开启 ASan/UBSan | [主机测试](#新架构主机测试) | 几分钟 |
| 界面预览 | 每一页在四种屏上实际画出来的样子 | [`tools/ui_preview.py`](#在电脑上预览界面) | 每款几分钟 |
| 构建核验 | 受影响产品的完整编译，核对有效配置和产物 | `python scripts/build.py <板>` | 每块板几分钟 |
| 设备回归 | 两台设备之间的通话、AI、微信、抓包、内存 | [按当前固件选择工具和词表](#设备回归) | 按场景 |
| 真人确认 | 听感、触摸手感、实体按键 | 人工 | 按需 |

## 改完代码跑哪些测试

先让工具算出受影响的产品和该跑的测试：

```bash
python scripts/check_change_impact.py --files sdk/xiaotai_media/src/processors/echo_gate.c
```

它会列出受影响的产品、要编译的板，以及对应的主机测试。没被列出的产品，不代表一定没有影响：间接包含的头文件和生成的源码，仍然要人工看一下编译图。

它按产品清单和变体算出消费者；五款产品都只走 SDK 入口。

常用的主机测试：

```bash
python tests/fetch_components.py             # 准备锁定的组件源码，首次或升级依赖后运行
python tests/run_host.py                     # 全部主机测试，需要 Linux 和对应的编译器
python3 tests/sdk/run.py                     # SDK 组件、板包和五款产品
python tests/test_products.py                # 产品清单和生成图
python tests/test_flash_layout.py            # 烧录分段
```

五款 SDK 产品的生成和启动测试在 `tests/sdk/product/`。各模块的专项测试按目录分在 `tests/` 下。详见 [tests/README.md](../tests/README.md)。

### 新架构主机测试

在 Linux 或 WSL 下，从仓库根目录运行：

```bash
python3 -B tests/sdk/run.py
python3 -B tests/sdk/product/run.py --product xiaotai-szpi-s3 --product xiaotai-cores3-lite \
  --product xiaotai-waveshare-p4-rev3 --product xiaotai-wt99p461-s1-1v1
```

第一条跑组件、公开头文件和各板包；第二条用四款默认产品的实际选型启动，覆盖冷启动、已保存网络、抢占和 AI 会话启停等场景。Wi-Fi、云和媒体零件用主机假后端，结果不代表真机内存和听感。整机测试如果让模拟外部栈直接调用有缓存关闭风险的端口，会报告任务名和操作名并失败。只想测某个变体或单板时，见[生成产品主机回归](../tests/sdk/product/README.md)。

### 在电脑上预览界面

改了主题、页面文字或布局，先在电脑上看一眼，不用烧板。在 Linux 或 WSL 的仓库根目录：

```bash
python3 tests/fetch_components.py --set all          # 第一次运行前准备 LVGL 等主机组件
python3 tools/ui_preview.py                          # 四款彩屏
python3 tools/ui_preview.py --product xiaotai-szpi-s3 --out build/ui-preview
```

工具用真实的产品、板包、主题和 LVGL 在主机上运行，自动点遍能点到的页面，再演示一次 AI 对讲和一次设备来电，每一帧存成 PNG，总览在 `build/ui-preview/index.html`。旋转安装的屏（例如微雪 P4）按固件同样的方式旋转后再存图，所以看到的就是屏上的方向。产品主机测试里的 `screens` 场景跑的是同一段代码，保证它一直能运行。改界面的规范见技能 `xiaotai-ui`。

## 设备回归

工具在 [tools/xt](../tools/xt/README.md)。立创 S3 的 SDK 默认镜像未开放物理 AT，用启动日志核对运行身份。对开放物理 AT 的镜像（如 CoreS3-Lite 和微雪 P4 的默认固件），核对完整 ELF SHA-256、该构建的 `commands.json` 和实时 `AT+HELP`。先读状态，再给需要的动作逐条授权；不同镜像的结果分开记录。

### 统一 SDK 固件

设备在线但原因不明时，先取一份只读快照。怀疑栈不足，再按当前构建里实际存在的任务名取水位：

```bash
python tools/xt/xt.py snapshot DEV --commands "$COMMANDS" --elf-sha256 "$ELF_SHA256" \
  --output snapshot.json
python tools/xt/xt.py app-stacks DEV --commands "$COMMANDS" --elf-sha256 "$ELF_SHA256" \
  --expect-task xiaotai --workers
```

`DEV` 可用串口名；`COMMANDS` 指向该构建的 `commands.json`，`ELF_SHA256` 为完整指纹。示例的 `xiaotai` 是独立的框架任务；有的构建没有它，按本机实际任务名替换。快照、任务栈、传输和平台两个专用水位是独立证据：缺项记未测，单个任务达标不代表全部通过。

有原生 USB Serial/JTAG、且开放物理 AT 的 ESP32-S3 和 ESP32-C3，可以自动核对芯片复位。比如已知首页应用是 `companion` 的固件，在设备空闲并确认要复位时运行：

```bash
python tools/xt/xt.py boot-check "$PORT" --usb-serial "$USB_SERIAL" --commands "$COMMANDS" \
  --elf-sha256 "$ELF_SHA256" --expect-app companion --rounds 3 --allow USB_CHIP_RESET
```

三轮分别核对 ROM 重启原因、应用身份和 Wi-Fi、平台在线。芯片复位不等于整板断电。关闭 AT 的默认镜像要看启动日志，不能拿诊断镜像的结果代签。

要发起通话、AI 或多轮测试，按 [SDK 台架命令和授权示例](../tools/xt/README.md) 执行。统一 SDK 的 `soak` 跑 AI，设备互呼单独用 `call`；不要在新固件上照抄旧版的 `soak --peer`。

## 出了问题，先判断是哪一层

不要凭听感或一条日志猜原因。先用一条命令拿到证据，再按下面的顺序从低层往高层找，找到第一处异常为止：

```text
声学/硬件 → 驱动 → 音频处理（AEC、回声门、噪声门、AGC）→ 编码
→ 传输（TiRTC 帧）→ 网络/平台（Wi-Fi、MQTT、HTTP、服务端）→ 业务状态 → 界面
                       内存贯穿所有层
```

| 现象 | 先跑 | 看什么 |
| --- | --- | --- |
| 通话一方听不清、断续、声音小 | `xt.py trace A B -s 18`，通话中对着 A 说话 | 两个方向的帧校验值匹配率；A 发送的帧有没有被回声门或噪声门压掉 |
| 通话里完全听不到某一方 | `xt.py call A B` | 那一方发出的帧数是不是 0；日志里 `uplink gated` 的原因，比如用户关了麦克风 |
| 对方挂断后，本机卡在失败页 | `xt.py call B A`，让 B 挂断 | 本机有没有打印 `invalid hangup command`，错误码是不是 `-40008` |
| AI 回复丢字、卡顿 | `xt.py ai DEV -s 60` | 下行丢帧 `rx_dropped`、`RX BACKPRESSURE`、最低内存水位 |
| 掉线 | 先取快照；需要时间线再开日志 | 区分 Wi-Fi、MQTT 和平台，记录第一次异常以及有没有自动恢复 |
| 多跑几轮后内存变少 | 按入口选对应的 `soak` | 比较同一启动、同样空闲条件下的内部堆和最大连续块；统一 SDK 首轮前和末轮后各静置至少 130 秒 |
| 冷启动在首次 NVS 分区映射失败 | 从启动第一处错误回溯；看 `cache-unsafe task stack` | 哪个任务调用了哪个端口。确认分区映射、存储或 PHY 校准确实交给内部栈任务，保留 NVS 现场 |

几条判断规则：

- **先看送达的帧**：匹配率高只说明采到的两端帧大体一致。句首缺帧、晚到或播放欠载也可能影响听感；保留时间戳和播放计数，再决定查传输、播放还是声学。
- **发送端处理的问题**：同一帧在发送端的麦克风电平高，发出去的电平却很低，状态是 closed 或 attenuated。说明是回声门或噪声门压掉了。
- **下行的问题**：分别看 UDP 邮箱满、已收到帧的时间戳、应用接收队列拒收和播放器欠载。它们的单位和观察范围不同，别相加当作丢包数。MQTT 重连只说明信令变化，不证明 RTC 媒体丢包。队列容量也不等于播放延迟；需要同时记录包到达和出队时刻。
- **业务状态的问题**：媒体帧都正常，但会话阶段或错误码不对，或者命令被判为无效。
- **内存持续下降**：先核实连接和任务确实释放，TCP 等待期已结束。总空闲恢复、最大连续块没恢复时，分别记录；一次低水位或下降斜率只能提示继续查，不能单独证明泄漏。

完整的判定方法和以往的案例在 `.claude/skills/xiaotai-verify/references/` 里。用 Claude Code 时，直接描述现象，`xiaotai-verify` 技能会按这套方法取证。

## 改音频处理前的规则

- 回声门、噪声门、AEC 相关的改动，必须先通过主机测试里的两机互呼防啸叫仿真（`sdk/xiaotai_media` 的 `media_echo_gate`），再上板。
- 门限和时间常数，先用 `trace.json` 里的真实电平离线回放调好，再写进代码。
- 一次只改一个变量。改完用同一条命令复测，对比两次的 `summary.json`。

## 报问题时提供什么

板型、固件版本（`AT+VERSION`）、复现步骤、期望的结果、实际看到的现象，以及 `runs/` 里对应的目录。先删掉日志里的 Wi-Fi 密码、Token 和绑定码。
