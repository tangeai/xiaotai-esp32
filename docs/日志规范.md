# 日志规范

[返回首页](../README.md) · [开发指南](开发指南.md) · [测试与诊断](测试与诊断.md) · [AT 指令](AT指令.md)

这份文档讲串口日志：有哪几级、每一级给谁看、一行日志怎么写、什么不能打，以及运行时怎么调级别。写新模块或改旧日志前先读它；接上串口想看懂设备在干什么，读前两节就够。

## 默认看到什么

默认级别下，日志是一条主线：设备是什么固件、联没联上网、平台在不在线、每次对讲和通话什么时候开始、怎么结束，出错时原因是什么、下一步查什么。不用查文档就能读懂。

```text
I (1436) xiaotai: XiaoTai 0.3.2-dev on esp32s31, ESP-IDF v6.1, elf=75eeaabe
I (1437) xiaotai: board=guition-jc1060f570c revision=1.0
I (1445) identity: device credentials: valid
I (1587) framework: started
I (1643) net: connecting (attempt 1)
I (1786) wake: wake word nihaoxiaotai ready, threshold 900/1000
I (4007) net: connected ip=192.168.1.23 channel=11 gen=1
I (6083) transport: online
I (6309) platform: online: logged in, signaling subscribed
I (26518) ai_talk: started gen=3 (by the user)
I (51508) ai_talk: ended gen=3: stopped here after 24 s
I (57634) call: outgoing gen=5
I (71526) call: ended gen=5: hung up here
```

出错时也是一行说清，例如麦克风静音时开始对讲：`W (26981) ai_talk: start refused: the microphone is muted: unmute it first (error 0x103)`。

芯片 ROM 的几行（`ESP-ROM:`、`rst:` 等）不归固件管，照常出现，其中 `rst:` 是上次复位的原因。ESP-IDF、驱动和第三方库自己的日志默认只出警告和错误，所以平时看不到 Wi-Fi 驱动、PSRAM、堆初始化那几百行。

## 级别

一共两类日志，各有一个级别，互不影响。

| 目标 | 管什么 | 默认 | 取值 |
| --- | --- | --- | --- |
| `app` | 小钛自己的日志（下文的四个宏和事件日志） | 3 信息 | 0 关、1 错误、2 警告、3 信息、4 调试 |
| `sys` | ESP-IDF、驱动、第三方库自己的日志 | 2 警告 | 0 关、1 错误、2 警告、3 信息 |

`app` 的四级各给谁看：

| 级别 | 宏 | 给谁看 | 写什么 |
| --- | --- | --- | --- |
| 错误 `E` | `XIAOTAI_LOGE` | 所有人 | 一件事失败了：哪件事、原因（错误码或文字），能给建议就给 |
| 警告 `W` | `XIAOTAI_LOGW` | 所有人 | 已经处理、但值得看一眼：重试、被拒绝、降级；被拒绝要写原因 |
| 信息 `I` | `XIAOTAI_LOGI` | 普通开发者 | 主线：开发者会叫得出名字的一步，一步一行 |
| 调试 `D` | `XIAOTAI_LOGD` | 调试这个模块的人 | 状态机迁移、协议往来、时序和耗时、内存水位、音视频统计 |

判断一行该放哪一级，问两个问题：

1. 不了解这个模块内部的人，读到这一行能明白发生了什么吗？不能就是调试级。
2. 一次正常的开机、对讲或通话里，这一行会出现几次？超过一两次的不进信息级；周期性输出的一律是调试级。

调试级的内容编进了每一款固件，平时不输出、不格式化，打开才有。Flash 特别紧的产品可以在产品清单的 `sdkconfig` 里把 `CONFIG_XIAOTAI_LOG_LEVEL_CEILING` 设成 `3`，调试级的文字就不进镜像，`AT+LOGLEVEL` 回包里的 `max` 会如实显示。

## 运行时调级别

串口上两种写法都行，对照表在 [AT 指令](AT指令.md) 的“通用维护命令”。

| 要做什么 | 通用命令 | AT 指令 |
| --- | --- | --- |
| 看当前级别 | `log-level` | `AT+LOGLEVEL` |
| 打开全部调试日志 | `log-level app 4` | `AT+LOGLEVEL APP 4` |
| 只看一个模块的调试日志 | `log-level module media 4` | `AT+LOGLEVEL MODULE media 4` |
| 让一个模块安静 | `log-level module camera.dvp 1` | `AT+LOGLEVEL MODULE camera.dvp 1` |
| 模块恢复跟随 `app` | `log-level module media -` | `AT+LOGLEVEL MODULE media -` |
| 看 ESP-IDF 和第三方库的信息级日志 | `log-level sys 3` | `AT+LOGLEVEL SYS 3` |
| 把当前的 `app` 和 `sys` 级别存下来 | `log-level save` | `AT+LOGLEVEL SAVE` |
| 不再保存，下次开机回到默认 | `log-level forget` | `AT+LOGLEVEL FORGET` |
| TiRTC 自己的日志 | `log-level tirtc <0..17>` | `AT+LOGLEVEL TIRTC <n>` |

- 模块名就是日志行里冒号前的那个词，见下面的[模块标签](#模块标签)。同时最多给 4 个模块单独定级别。
- 级别默认不保存，重启后回到 `app 3`、`sys 2`。要看开机和联网过程的调试日志，先 `log-level app 4`、`log-level save` 再重启；查完记得 `log-level forget`。保存的只有 `app` 和 `sys` 两个级别，模块级别和 TiRTC 级别不保存。
- `log-level tirtc` 大于 0 时，TiRTC 自己的日志会原样打出来（标签 `tirtc`），其中可能有密钥或令牌，分享前要删掉。
- 重启先打一行 `framework: restarting: <原因>`。芯片真正复位的那一刻，默认级别下只留小钛的错误日志：驱动和连接这时被拆除，打出来的告警都是预料之中的。`app` 调到 4 或 `sys` 调到 3 时不静音。

## 一行日志怎么写

格式固定是 `<级别> (<开机后的毫秒数>) <模块>: <内容>`，由宏生成，调用时只给模块名和内容：

```c
#include "xiaotai/port/log.h"

XIAOTAI_LOGI("call", "outgoing gen=%" PRIu32, session);
XIAOTAI_LOGW("ai_talk", "start refused: %s (error 0x%x)", why, (unsigned)err);
XIAOTAI_LOGD("media", "downlink holds %u ms in %u bytes", hold_ms, bytes);
```

内容的写法：

| 规则 | 好 | 不好 |
| --- | --- | --- |
| 先写发生了什么，用模块自己的固定词 | `ended gen=3: the peer hung up after 42 s` | `call state changed to 0 reason 2` |
| 数字带名字，要单位就带单位 | `next attempt in 4000 ms`、`free=158432 bytes` | `4000`、`value=2` |
| 会话类的事带上代次 `gen=`，前后几行靠它对上 | `started gen=2` … `ended gen=2` | 开始和结束对不上是哪一次 |
| 枚举值写成词 | `link lost: authentication failed` | `loss=3` |
| 失败和拒绝写原因，能给建议就给 | `start refused: the microphone is muted: unmute it first` | `start failed` |
| 一件事一行，开始一行、结束一行，统计放在结束那一行 | `ended gen=2: stopped here after 25 s` | 过程中每秒一行 |
| 不带文件名、函数名、行号 | `storage: async write failed: 262` | `kv_worker.c:342 write_job() failed` |
| 英文、小写开头、不加句号 | `connected ip=192.168.1.23 channel=11` | `Connected Successfully!` |

模块名用小写字母、数字、下划线和点，最长 15 个字符，一个模块只用一个，和它在事件日志里的来源名相同。

### 什么不能打

- **实时路径不打日志。** 采集、播放、编解码、传输回调，以及任何每包、每帧、每 20 ms 跑一次的地方，只加计数器；统计通过事件日志的主题（见下节）低频输出，会话结束时写一行汇总。错误可以打，但同一个错误要限次数。
- **秘密和身份不进日志。** 设备号、设备密钥、令牌、绑定码、Wi-Fi 名称和密码、用户说的话和字幕、联系人名字，一律不打，也不能编码进数字里。IP 地址、信道、错误码可以打。
- **不为日志申请内存。** 日志调用不分配内存；内容在调用者的栈上按格式直接输出，不要先拼进大缓冲再打。
- **准备数据也要省。** 只为一行调试日志去读统计、算表格时，先用 `xiaotai_log_enabled(XIAOTAI_LOG_LEVEL_DEBUG, "模块")` 判断，级别没开就整段跳过。

## 事件日志和日志的分工

[事件日志](SDK架构.md)（`xiaotai/eventlog.h`）是给工具读的：固定标签加一个数字，存在内存环里，`AT+LOG` 和台架脚本读它，实时任务也能记。它和串口日志的关系：

| 事件日志里的 | 串口日志上 | 用在哪 |
| --- | --- | --- |
| 信息级事件 `xiaotai_eventlog_note` | 信息级一行：`I (…) call: incoming gen=5` | 标签本身读得懂的主线步骤 |
| 警告、错误事件 | 同级一行，带 `error=0x…`、`link=…` | 处理了的异常和失败 |
| 调试级事件 `xiaotai_eventlog_debug` | 调试级一行 | 内部阶段、释放确认这类只有调试者关心的步骤 |
| 只记录 `xiaotai_eventlog_record` | 不输出 | 模块已经另写一行完整日志的步骤 |
| 主题（实时统计，`xiaotai_eventlog_post`） | 调试级，每个主题最多 5 秒一行；警告、错误级的主题按原级输出 | 采集电平、播放节奏、收发计数 |

事件环里的内容不受级别影响，`AT+LOG`、`AT+LOG TOPICS` 任何时候都读得到全部事件和主题的最新值；级别只决定它们要不要同时打到串口上。

标签读不懂、要带原因或时长的步骤（比如通话结束），在模块里另写一行信息级日志把话说清楚，对应的事件改用 `xiaotai_eventlog_record`，两边不重复。

| `xiaotai` | 启动入口：固件身份、板子、启动失败 |

| `companion`、`door`、`alarm` | 应用 |

## 系统和第三方日志

ESP-IDF 和第三方组件用它们自己的宏打日志，源码不改，只在运行时调级别：

- 构建默认 `CONFIG_LOG_DEFAULT_LEVEL_WARN`、`CONFIG_LOG_MAXIMUM_LEVEL_INFO`、`CONFIG_BOOTLOADER_LOG_LEVEL_WARN`（`config/xiaotai.defaults`）。信息级的文字还在镜像里，`log-level sys 3` 随时能打开；引导程序的信息级日志不再输出。
- 有几个标签在这款固件里“警告”的是正常情况，默认压到错误级，`sys` 调到 3 时全部放开。名单在 `sdk/xiaotai_port/esp-idf/log.c`，加之前先确认那条警告对应的状况已经由小钛自己的日志报告了：

| 标签 | 压掉的警告 | 为什么是正常的 |
| --- | --- | --- |
| `wifi` | 速率表、每个块确认会话 | 驱动例行输出；断线原因由 `net` 用文字报告 |
| `AFE_CONFIG` | `wakenet model not found` | 唤醒词在小钛自己的引擎里跑，不放进音频前端 |
| `i2s_common` | `rx channel … switched from master to slave` | 全双工 I2S 就是这样打开的 |

- TiRTC 库的版本信息行（带颜色、`[tiRTC] Build Info:` 开头）和建链时的 `peer_connection state change e=…`，由库直接写到串口，不经过日志系统，级别管不到它们。

## 改日志时的检查

1. 改完在设备上各抓一份默认级别和调试级别的日志，走一遍开机、联网、一次对讲、一次通话，数行数和每秒字节数，和改之前比。空闲时默认级别应该没有周期性输出。
2. 主机测试：`python3 -B tests/sdk/run.py xiaotai_port xiaotai_eventlog xiaotai_at`，以及改到的模块。
3. 没有外部内存的产品还要比固件大小和静态内存：日志改动不应该增加运行时的内存申请。
