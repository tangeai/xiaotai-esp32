# 新板适配与兼容性契约

本指南面向多芯片分支的硬件、媒体、交互和产品适配。

## 目标与当前进度

目标是“硬件适配 + 选择现成交互/业务组合”。同类新板只实现硬件端口和能力描述；新交互形态只增加交互适配器，不改业务状态机。缺少能力、SDK 或媒体适配时给出明确错误，不自动删功能、换协议或套用其他板的引脚。

六个板型已接入硬件、媒体、交互与产品之间的**构建前契约检查**。运行时仍有板型专用实现，接入新板时除了硬件，还需核对相应业务和媒体依赖。构建证据和真机边界见[验证范围](VALIDATION.md)。

不要把能力清单当成驱动实现或硬件自检。构建报告明确记录 `runtime_portable: false` 和 `hardware_tested: false`。

## 四个选择轴

| 选择轴 | 回答的问题 | 不承担的职责 |
| --- | --- | --- |
| Hardware | 有哪些可用端口、接线、资源和约束 | 不决定 AI、呼叫协议、联系人或页面 |
| Media Adapter | 如何将物理采集/播放转换为明确的帧流 | 不从屏幕类型猜编码，不管理业务会话 |
| Interaction Adapter | 怎样把输入转换为意图，把状态转换为可感知反馈 | 不直接创建/释放 RTC，不自建通话状态机 |
| Product Policy | 开哪些业务、使用哪些交互/媒体实现和 SDK | 不写 GPIO、总线、触摸坐标或 codec 初始化 |

`芯片型号`只约束工具链、SDK ABI 和可用实现；`板卡型号`只选择物理适配；`无屏`不等于无交互；`有相机`不等于支持视频呼叫。

能力表同时记录板级与平台组合能提供的最低条件。`network.ip` 仅表示所选原生 Wi-Fi/Hosted 路径可提供 IP 承载，`storage.nvs` 表示平台持久化可用；它们不把配网状态机、云身份、绑定和业务存储所有权移入 Board。

## 运行时分层

下面是后续实现的明确责任边界，**接口设计尚未全部落为通用运行时实现**，不新增只声明、不被调用的 C++ 外壳。

```text
物理输入 -> InputPort -> InteractionAdapter -> IntentSink
                                                 |
                                      原应用/业务状态机
                                                 |
                                      状态快照与操作结果
                                                 v
显示/灯光/声音 <- FeedbackPort <- InteractionAdapter

原应用/业务状态机 -> MediaSession -> MediaAdapter -> HardwarePorts
                -> TiRTC 适配层（连接、generation、收发契约）
```

| 接口 | 必须说清的契约 | 唯一所有者 |
| --- | --- | --- |
| Board / HardwarePorts | 创建 typed 端口；型号/版本与能力；总线共享、资源冲突、初始化/回收 | BSP/驱动；不持云身份和业务状态 |
| PcmCapture / PcmPlayback | 采样率、声道、位宽、交错格式、帧长、单位、超时；部分读写与 DMA 缓冲寿命 | 音频驱动；AEC/重采样属于媒体层 |
| EncodedCapture | codec、采样率、声道、包时长、最大包、时间戳及缓冲所有权 | 编码外设驱动；VB6824 Opus 不伪装为 PCM |
| CameraPort | 输出格式、尺寸、时间戳、帧借用/归还、最大队列、停止后的回调规则 | 相机驱动；业务决定是否上传/订阅 |
| DisplayPort | 逻辑 viewport、像素格式、stride、字节序、rotation、flush 完成语义 | 显示驱动；页面对象不进入 Board |
| InputPort | key/pointer/encoder 等原始事件、单调时间、来源、边界坐标 | 输入驱动；长按含义和当前动作由交互层决定 |
| FeedbackPort | 灯效、声音、振动等独立输出；优先级、取消与占用 | 驱动持设备，媒体/应用仲裁扬声器；振动为未来端口 |
| IntentSink | 有界命令投递、request id、会话代次、明确接受/拒绝结果 | 原应用事件循环；接受入队不等于操作完成 |
| SnapshotSource | 只读状态、副本/寿命、版本号、会话 generation、绑定状态、能力与错误 | 原状态机；UI 不反向修改业务状态 |

C++ 用于端口/适配器/编排；C 驱动和 TiRTC 接口保留，经窄 C ABI 桥接。C 回调不得跨 ABI 抛异常，不把 IDF、LVGL、TiRTC 具体类型泄漏到纯业务接口。

### 生命周期与错误

- 端口区分“未提供能力”“初始化失败”“忙”“超时”“取消”“资源回收失败”，不能统一返回成功或空对象继续启动。
- 启动顺序和回收顺序由资源所有者记录；初始化失败只逆序清理已获得资源。清理失败保留句柄和错误，禁止假装 Cold 后重建第二个所有者。
- 保留现有 wake token、playback epoch、session generation 和命令发布顺序。UI 快照不能取代连接代次；销毁后迟到回调必须由原所有者识别。
- SDK/ISR/定时器回调只做有界复制和投递，不执行阻塞 HTTP、NVS、Stop/Uninit、声音播报等待或显示重建。
- 队列满必须显式返回错误并保留计数。指针移动等可合并事件和接听/挂断等不可丢命令分开；不能因“防抖”吞掉状态转换。
- 原业务状态机保持单一所有者。公共适配层只做映射，不并行运行第二套通话状态机。

## 无屏与多种交互

交互要覆盖完整任务，而不只是替换画图函数。

| 任务 | 彩屏/触摸 | OLED/按键 | 无屏/按键/灯/声音 |
| --- | --- | --- | --- |
| 配网/失败 | 页面、触摸确认 | 导航、确认、状态文本 | 有限手势、灯效、可区分的声音反馈 |
| 绑定 | 展示真实绑定状态/码 | 文本及已有播码 | 完整真实六位码播报、可重复、可取消；绑定变化撤销旧播报 |
| 来电/接听/拒绝/挂断 | 对应页面与按钮 | 当前上下文中的键意图 | 明确区分来电、连接中、通话、结束；保留原单击/双击语义 |
| 联系人/房间 | 列表、选择 | 分页/滚动/确认 | 由产品选择可达交互；当前 MZ28 未实现这些业务，不自动增加 |
| 错误与恢复 | 状态和动作结果 | 短文本/声音 | 灯/声音可感知失败，不能仅写串口日志 |
| 设置/重置 | 确认流程 | 返回/确认 | 有意的手势与明确确认；不因无屏自动接受破坏性操作 |

旋钮映射 Navigate/Confirm/Back；遥控、远程输入等通过独立适配器变成相同意图。远程输入仍须经过鉴权和权限判断，不能把本地按键入口直接暴露给网络。多输入并存时保留来源、上下文 epoch 和会话代次，防止旧页面手势控制新会话。

语音命令在识别器输出后进入交互适配器，原始音频仍走媒体端口；触摸手势、串口外设和传感器事件也分别映射，不让 Board 按当前业务状态解释它们。新增输入/反馈类型需补端口实现、明确的事件单位与测试，再登记能力词汇，不采用任意字符串透传。

没有屏幕也没有按键的产品，必须先有可用的配网、绑定、授权控制及失败反馈路径，才能注册产品。当前没有此类产品实现；测试中的远程输入只证明契约组合规则，不代表已实现这类固件。

## 媒体兼容性

必须独立记录三种格式：硬件格式、内部处理格式、每个业务/方向的传输格式。每项至少包含 codec、rate、channels、sample/packet duration、timestamp、stream id 和缓冲寿命。转换必须由已选择的媒体适配器实现，不能靠“两个设备都有麦克风”推断兼容。

这轮源码复查发现，CoreS3 的旧配置标签也是 `opus16k`，但 [真实头文件](../main/xiaotai/transport/cores3/starter_tirtc/include/starter_tirtc.h) 明确区分 H5/AI/房间的 PCMA 8 kHz 与呼叫/微信的 Opus 16 kHz，物理 PCM 保持 16 kHz。因此新 `pcm-host-codecs` 只描述硬件端口需求，不规定所有业务采用同一个 codec，也不改写旧协议。

Xmini 的 PCMA 与 OLED 是两个独立选择；MZ28 的 Opus 上行与 PCM 下行是两个端口。相机采集、JPEG/H.264 编解码、视频发送/接收、预览是独立能力，后续不可压缩为一个 `has_camera` 开关。当前能力检查中的 `camera.capture` 仅检查现有产品的最低采集需求，不替代完整视频格式/解码能力检查。

PSRAM、内部 DMA 堆、任务栈、队列上限和 Flash 分区也属于兼容条件。`memory.psram` 只是最低资源前提，不证明可用容量或运行余量；现有 S3/WT APP 空间紧张，不能用静默裁剪 UI/资源的方式适配。

## 已落地的构建契约

| 文件 | 内容 |
| --- | --- |
| `main/boards/<board>/capabilities.json` | 实现所需的硬件能力描述；display 为完成板级旋转后的 viewport，不是面板原始扫描方向 |
| [媒体与交互契约](../config/adapter-contracts.json) | 当前实现所需端口、可选输入组、精确的像素格式/尺寸；这些是需求描述，不是新运行时驱动 |
| [产品契约](../config/product-contracts.json) | 六板原功能集、原 source profile、SDK 变体、媒体与交互选择；当前标记 `native-bound` |
| [契约检查器](../scripts/product_contract.py) | 字段/能力拼写、依赖、缺失端口、显示、SDK/profile 一致性和禁止错误跨板复用 |
| [构建入口](../scripts/xiaotai_build.py) | list/plan/configure 使用同一检查；四份契约输入的 SHA-256 进入 requested/build record/输入清单 |
| [契约回归](../tests/test_product_contracts.py) | 使用真实构建检查函数，而非另一份测试专用判断逻辑 |

无屏产品明确选择 `headless-key-led-voice`，其按键、RGB 灯、声音反馈都为必需项。未知字段、重复能力、错误尺寸和错用 PCM/UART 直接报错。现有产品仍保留原完整功能集；新产品选择和功能裁剪不能仅修改 JSON 后就宣称已验证。

结构检查保留原六板必需项，但不再以“仓库只能有六板”限制新板注册。构建目录隔离检查按实际注册数量执行；新增 SDK/新 profile 仍须通过各自接口和源码检查。Windows 静态检查曾因系统 GBK 默认编码读取中文源码失败，已改为显式 UTF-8，并增加调用真实审查函数的编码回归。

当前两块 320×240 S3 在硬件最低需求上可以互相匹配，但其 driver/source graph 不可互换。`native-bound` 检查故意拦截改名套用，防止把形式上的通用性误当成真实可移植性。待运行时端口迁移与独立新板验证完成后，才能对对应产品解除这个限制。

这是过渡契约：`product-contracts.json` 与原板级 `config.json` 交叉校验，防止迁移期间无意改变功能、UI 或 SDK。运行时解耦后，应由独立产品配置作为唯一组合来源，板级目录只留硬件与构建条件，不长期维护两份业务配置。当前不开放任意 `--ui`/`--audio` 参数，以免检查通过而实际仍启动旧 profile。

## 兼容性验收矩阵

| 检查层 | 检查要求 | 证据边界 |
| --- | --- | --- |
| 契约正反例 | 13 个测试方法；六板与六产品 36 对组合；逐个删除必需能力；类型、未知字段、错误屏幕/媒体、协议标签与 source profile 漂移 | 主机规则检查，不探测硬件 |
| 非同名新板 | 合成的无屏 PCMA、旋钮、远程输入；使用现有需求函数验证组合不依赖型号或 OLED | 仅规则 fixture，没有宣称存在这些新板实现 |
| 真实六板构建 | IDF/SDK/依赖锁、有效 sdkconfig、唯一入口、架构/分区、契约输入哈希 | 六个默认产品；不等于任意组合可编译 |
| 链接图隔离 | 无屏/C3 不引入彩屏、PSRAM 和不需要的视频后端；Mini/通用 C3 库不串用 | 复用现有构建图审核；非默认组合仍未验证 |
| 交互主机回放 | 同一业务事件序列分别送彩屏/OLED/无屏适配器；比较意图、快照、错误、播报取消、重复操作 | 通用适配器尚待实现，不能用 JSON 测试代替 |
| 资源/失败注入 | 所有端口 open/start/stop/close 失败、队列满、删除失败、迟到回调、输入 epoch 更新、格式不支持 | 已有专项覆盖部分原所有者；公共端口全矩阵尚待实现 |
| 媒体格式 | 每产品×业务×方向检查采样/codec/分包/流号；错误格式拒收和原协议回归 | 继续保留原专项，不从 `audio` 简称推断 PASS |
| 新板接入证明 | 用非六板身份、不同引脚且复用现有实现的板级 fixture；业务源码零差异，依赖图不含旧 BSP | 尚未完成；是通用化前期收口必需项 |
| 真机兼容 | 上电/设备探测、屏幕/无屏完整操作、Wi-Fi/绑定、音视频/回声、内存/栈、异常恢复、弱网/长稳 | 按目标板单独验证，不从静态检查或构建结果推断 |

## 新板接入步骤

1. 确认芯片 SDK、ABI、Flash/PSRAM 与工具链支持。没有对应 SDK 的新芯片先做独立 SDK 验证。
2. 实现板级 typed 端口，描述接线、时钟、供电、共享总线、DMA/缓存限制、回收和错误语义。复用成熟驱动但不复用别板引脚。
3. 选择已实现媒体适配器、产品业务和交互适配器，执行能力匹配。当前 `native-bound` 产品须先完成下节的端口迁移，不能直接复制入口。
4. 同类交互不改业务；新交互只实现 Intent/Snapshot 映射与 Feedback。新增编解码/外设协议在媒体/驱动责任层适配。
5. 跑契约反例、主机失败注入、构建及链接图隔离；检查有效配置与产物身份。先证明业务源码不需要板名分支，再进入后续真机验收。

## 剩余前期工作

1. 从现有 S3 `CodecBoard`/硬件所有者拆出有生命周期与格式描述的 typed 端口，移走 UI/媒体中的板型判断和 GPIO 初始化；CoreS3 作为同类复用验证。不能只扩充 Board 的方法数量。
2. 把现有 Xmini 意图/快照机制与 MZ28 命令/灯/播报入口映射到共同交互边界，保持各自 C 状态机、手势、会话代次和 Mini 命令顺序。彩屏也接入同一方向的意图/快照，不由 UI 直接管理媒体资源。
3. 接入 P4 视频/显示和 WT 专用外设契约，分开采集、显示、解码、触摸、协处理器网络，保留各板差异和原功能。
4. 完成跨交互事件回放、每业务媒体格式和独立新板 fixture，再重新整体 review。此后才能把 `runtime_portable` 与前期收口状态改为完成。

以上是通用化尚未覆盖的范围，既有板型构建通过不代表新板可以直接复用。
