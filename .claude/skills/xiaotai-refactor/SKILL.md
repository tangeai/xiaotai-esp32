# 结构整理

目标：**代码只有一份，差异是数据**。衡量标准是“加一块板、换一块板要改几处”。整理本身不改变任何产品的行为；要改行为，就单独做、单独测。架构说明在 `docs/SDK架构.md`。

## 先确定改哪一层

```text
产品（products/）→ 应用（apps/）→ 模块（sdk/modules/）→ 框架 → 引擎 → HAL / 零件（sdk/parts/）→ 端口
板包（boards/）只写这块板的硬件事实
```

| 要改的 | 放在哪 |
| --- | --- |
| 某款产品要不要某个功能、参数取多少 | `products/<产品>/product.json` 的模块、参数、变体 |
| 引脚、总线、供电、某块板独有的硬件 | `boards/<厂商>/<板>/` |
| 一种芯片或器件的驱动，几块板都可能用 | `sdk/parts/` |
| 一个业务功能（通话、闹钟、门禁） | `sdk/modules/` 加一个模块，用框架发意图、收事件 |
| 一种交互形态、一套页面 | `apps/` 和 `sdk/themes/` |
| 和 ESP-IDF、厂商库打交道的地方 | 端口层；只做适配，不改官方 SDK 和 IDF |

上层不包含下层的实现，`sdk/`、`apps/` 里不出现板名或产品名判断，`scripts/check_sdk_layers.py` 会拦。

## 1. 先给差异分类

对比两份副本（`git diff --no-index <A> <B>`，或逐文件比哈希），每个文件归入下面一类：

| 类别 | 例子 | 怎么办 |
| --- | --- | --- |
| 完全相同 | 两款 P4 的 `nvs_store` | 留一份，另一个产品的 `board.json` 指向它 |
| 一方是超集 | 一份多了诊断、多了可选功能 | 留超集；多出来的部分要是对另一方无害（默认关、按条件编译、弱符号），再合并 |
| 只差硬件事实 | 协处理器链路 SDIO/SPI、时钟、几路麦克风 | 留一份，按**已经存在的**事实选择：Kconfig 符号、`board.json` 的能力、板级端口。不要新造板名开关 |
| 双向分叉 | 两边各自加了对方没有的行为 | 先不合并。逐段决定要哪种行为，写进待办；等两块板都能上板验证再做 |

硬件事实本身（引脚、屏幕参数、相机型号）不要合并，搬进板包（`boards/<厂商>/<板>/`）。

## 2. 写成通用规则，不写个例

动手前先回答：这个差异的真正条件是什么？是有没有 PSRAM、几个麦、哪条 ESP-IDF 线、哪种联网链路，还是某个库的版本？

- 配置上的差异放进按能力生效的配置层（`config/capabilities/`），不在每块板的 `sdkconfig.xiaotai` 里各写一份。`tests/test_psram_policy.py` 会拦下重复的写法。
- 代码里的差异按能力或 Kconfig 选择，**不出现板名判断**。
- 测试按能力遍历所有产品，不点名某两块板：产品列表用 `scripts/product_scope.py`（树里没有的可选产品会自动跳过），组件和板包取 `scripts/sdk_selection.py` 对产品清单的解析结果。
- 按能力选缺省值，产品可以覆盖。例如板包的 `memory.external_ram` 决定资源档位：没有外部内存时常驻缓冲改成用时才申请、几个引擎合用任务；有外部内存的产品缺省行为不变。
- 一份代码两种形态，不是两套代码：精简形态必须能在任何产品上打开，包括有外部内存的。
- 确实只能个例处理的（某块板的硬件缺陷、某个库版本的问题），写清楚条件和什么时候可以删掉。

### 没有外部内存、放不下时

按这个顺序找，每一步都上板量：

1. **先量，不估。** 同一块板、同一场景，读联网空闲时的空闲量、最大连续块、会话中的最低值；按所有者列出堆块，和上一版逐项比。主机上的数和栈估算代替不了真机。
2. **系统配置对回上一版的值。** Wi-Fi、lwIP、mbedTLS、MQTT、HTTP 的缓冲个数和长度，系统任务栈。
3. **常驻改按需。** 上一版用时才申请的，这一版也用时才申请。
4. **任务栈按实测定。** 实测最深用量加 1 KB 或 25%，取大者；每种会话（AI、主叫、被叫、微信）都量过再定，不用主机上量的栈。
5. **合并任务先证明不阻塞。** 会同步等网络、等厂商库的调用，不能放进所有者或别的引擎的任务；合并前先跑时限测试。
6. **登记表、界面视图按实际数量生成**，能放进只读数据的就放进只读数据。

还不够时停下来，把每一步实际省下的量和剩余缺口列出来再设计下一轮，不绕过框架，也不给某款芯片单独裁一套代码。

## 3. 一次改完，再编译

1. 把同一个主题的改动一次做完：组件、`board.json`、CMake、测试、文档。
2. 静态预检：`python scripts/check_structure.py`、`python scripts/check_change_impact.py --files ...`，查头文件路径和被引用的符号。
3. `python scripts/build.py <板> --resolve-only` 确认依赖和配置能解析。
4. 受影响的产品一轮编译完，收齐错误一次修。

## 4. 证明行为不变

每一项都要有证据：

| 检查 | 怎么做 | 通过标准 |
| --- | --- | --- |
| 有效配置 | 比较改动前后每个产品构建目录里的 `sdkconfig` | 只差有意删掉的符号 |
| 产物 | 比较 `build-record.json` 里的应用大小 | 差异小且能解释（例如多编进一个可选诊断） |
| 依赖 | 比较 `dependencies.lock` | 不变 |
| 主机测试 | `python tests/run_host.py` | 全部通过 |
| 档位矩阵 | 按能力新加的形态，拿一款有外部内存的产品也打开跑一遍 | 全过，证明不是某款专用的路径 |
| 上板 | 至少一块受影响的板启动，并走一遍受影响的路径 | 日志里能看到选择器选对了分支 |

还有板子不在手上时，写明哪些产品只验证到编译。

## 5. 收尾

- 删掉旧副本时用 `git rm`，并检查文档和许可链接是否还指向旧路径。
- `CHANGELOG.md` 的“仓库整理”记一条：合并了什么、差异按什么选择、行为不变。
- 留下的双向分叉组件，列成清单交给用户：每一项写清两边各有什么、需要做什么取舍。
