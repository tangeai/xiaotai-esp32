# 结构整理

目标：**代码只有一份，差异是数据**。衡量标准是“加一块板、换一块板要改几处”。整理本身不改变任何产品的行为；要改行为，就单独做、单独测。

## 1. 先给差异分类

对比两份副本（`git diff --no-index <A> <B>`，或逐文件比哈希），每个文件归入下面一类：

| 类别 | 例子 | 怎么办 |
| --- | --- | --- |
| 完全相同 | 两款 P4 的 `nvs_store` | 留一份，另一个产品的 `board.json` 指向它 |
| 一方是超集 | 一份多了诊断、多了可选功能 | 留超集；多出来的部分要是对另一方无害（默认关、按条件编译、弱符号），再合并 |
| 只差硬件事实 | 协处理器链路 SDIO/SPI、时钟、几路麦克风 | 留一份，按**已经存在的**事实选择：Kconfig 符号、`board.json` 的能力、板级端口。不要新造板名开关 |
| 双向分叉 | 两边各自加了对方没有的行为 | 先不合并。逐段决定要哪种行为，写进待办；等两块板都能上板验证再做 |

硬件事实本身（引脚、屏幕参数、相机型号）不要合并，搬进板包（`boards/<厂商>/<板>/`）。

## 2. 写成通用规则，不写个例

动手前先回答：这个差异的真正条件是什么？是有没有 PSRAM、几个麦、哪条 ESP-IDF 线、哪种联网链路，还是某个库的版本？

- 配置上的差异放进按能力生效的配置层（`config/capabilities/`），不在每块板的 `sdkconfig.xiaotai` 里各写一份。`tests/test_psram_policy.py` 会拦下重复的写法。
- 代码里的差异按能力或 Kconfig 选择，**不出现板名判断**。
- 测试按能力遍历所有产品，组件目录从 `board.json` 解析（`tests/native_components.py`），不点名某两块板。
- 确实只能个例处理的（某块板的硬件缺陷、某个库版本的问题），写清楚条件和什么时候可以删掉。

## 3. 一次改完，再编译

1. 把同一个主题的改动一次做完：组件、`board.json`、CMake、测试、文档。
2. 静态预检：`python scripts/check_structure.py`、`python scripts/check_change_impact.py --files ...`，查头文件路径和被引用的符号。
3. `python scripts/build.py <板> --resolve-only` 确认依赖和配置能解析。
4. 受影响的产品一轮编译完，收齐错误一次修。

## 4. 证明行为不变

每一项都要有证据：

| 检查 | 怎么做 | 通过标准 |
| --- | --- | --- |
| 有效配置 | 比较改动前后每个产品构建目录里的 `sdkconfig` | 只差有意删掉的符号 |
| 产物 | 比较 `build-record.json` 里的应用大小 | 差异小且能解释（例如多编进一个可选诊断） |
| 依赖 | 比较 `dependencies.lock` | 不变 |
| 主机测试 | `python tests/run_host.py` | 全部通过 |
| 上板 | 至少一块受影响的板启动，并走一遍受影响的路径 | 日志里能看到选择器选对了分支 |

还有板子不在手上时，写明哪些产品只验证到编译。

## 5. 收尾

- 删掉旧副本时用 `git rm`，并检查文档和许可链接是否还指向旧路径。
- `CHANGELOG.md` 的“仓库整理”记一条：合并了什么、差异按什么选择、行为不变。
- 留下的双向分叉组件，列成清单交给用户：每一项写清两边各有什么、需要做什么取舍。
