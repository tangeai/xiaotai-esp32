# 小钛故障定界与验证

目标：**用最少的步骤，拿到能定位到“哪一层”的证据**，再改代码。不要凭听感或单个日志猜根因。

工具：`tools/xt/xt.py`（Python 3 + pyserial + esptool）。设备表从 `tools/xt/devices.example.json` 复制成 `devices.json` 后填写，本地文件不提交。所有测试结果自动存到 `tools/xt/runs/<时间>-<测试>/`，含两端原始日志、`summary.json` 和截图。

## 第一步：确认设备上跑的是什么，再按症状选命令

不同固件的指令和日志不一样，不先确认就会用错命令、读错数：

| 情况 | 怎么确认 |
| --- | --- |
| 开放物理 AT 的 SDK 固件 | `AT+VERSION` 有 `at=1`，`+BUILD: elf_sha256=` 的完整哈希和这次构建的记录逐字一致 |
| 不开放物理 AT 的默认固件（如立创 S3） | 看启动日志第一行 `xiaotai: XiaoTai <版本> on <芯片>, <平台>, elf=<ELF 前 8 位>`；没有 AT 回包不等于没启动 |
| 统一 SDK 之前的旧固件 | `AT+VERSION` 没有 `at=1`；指令按[判例](references/案例.md) 1 到 10 条的写法 |

同一块板烧过台架版、默认版、对照版时，每个结论都写清是哪个 ELF 得出的，不同镜像的数不能混在一起比。

已知是开放物理 AT 的 SDK 固件时，先跑 `python tools/xt/xt.py snapshot DEV --commands commands.json --elf-sha256 ELF_SHA256 --output snapshot.json`。只读快照不复位、不开始会话；指纹不符先停。先看 `summary.issues` 的异常、再看 `summary.unknown` 的缺测，需要时再按下表选专项。表里的命令对 SDK 固件都要带本次镜像的 `--commands`、`--elf-sha256`（两台设备再带对端的），会改变状态的指令逐条 `--allow`，写法见 `xiaotai-test` 第 4 节，下表省略不写。

| 症状 | 先跑 | 看哪几个数 | 详见 |
| --- | --- | --- | --- |
| 通话一方听不清/断续/小声 | `xt.py trace A B -s 18`（通话中让人对着 A 说话） | 两向校验值匹配率；A 发送帧的门控状态（open/attenuated/closed）；B 的上行门是否同时打开 | [定界方法 · 音频](references/定界方法.md#音频通话) |
| 对方或 AI 听到设备自己的声音（回声没消干净） | 单机测量 `xt.py echo DEV ...`，步骤和判断见 `xiaotai-echo` | 回声压低量、残余比底噪高多少、是否削顶 | `xiaotai-echo` |
| 通话完全听不到某一方 | `xt.py call A B` 再看该方 `uplink gated` 日志 | 发送帧数 tx 是否为 0；`muted=1`/会话/链路哪个条件挡住 | [案例 1](references/案例.md#1-m5-微信上行为-0闭麦偏好) |
| 对方挂断后本机卡在“呼叫失败” | `xt.py call B A`（让 B 挂） | 本机是否打印 `invalid hangup command`、错误码 `-40008` | [案例 2](references/案例.md#2-对端挂断后卡在呼叫失败) |

| 音频芯片开机打不开 | 启动日志 | 第一处 `Open fail` 的时间点，和各电源轨、复位脚上电的先后 | [案例 18](references/案例.md#18-音频芯片开机打不开共用电源轨被别的零件先拉低) |
| 内存申请失败 | `xt.py at DEV AT+MEM` | `+MEM-FAIL:` 的大小、caps、任务名；`min_free` 和最大连续块 | [案例 13](references/案例.md#13-ai-视觉申请内存失败常驻缓冲占掉了外部内存) |

| 掉线/离线 | `xt.py log DEV -s 600` 并 `xt.py at DEV AT+NET AT+PLATFORM` | MQTT EOF/重连、平台 epoch 增长、Wi-Fi RSSI | [定界方法 · 网络](references/定界方法.md#网络与平台) |
| 一直联不上网 | 读保存的网络：`xt.py at DEV AT+NET`（换网用 `AT+NET WIFI`，见 `docs/AT指令.md`“统一词表”） | 保存的 SSID 是否在现场；日志里是不是 `reason=201` | [案例 9](references/案例.md#9-p4-一直联不上网存的是旧网络) |

## 第二步：按层判定（从下往上，找第一处异常）

```text
声学/硬件 → 驱动(I2S/codec/屏) → 音频处理(AEC/回声门/噪声门/AGC) → 编码
→ 传输(TiRTC 帧) → 网络/平台(Wi-Fi/MQTT/HTTP/服务端) → 业务状态机 → UI/交互
                               内存/任务水位贯穿所有层
```

- **传输层没问题的判据**：`xt.py trace` 两向校验值匹配 ≥ 98%，且不匹配的只在首尾。此时“听不清”一定在两端的处理或声学，不要去查网络。
- **发送端处理的判据**：同一帧在 A 的 trace 里麦克风电平高（`pre`）、发送电平低（`db`）、状态是 closed/attenuated → A 的回声门/噪声门压掉了，网络无辜。
- **接收端播放的判据**：B 收到的帧校验值匹配、电平正常，但播放异常 → 查 B 的解码/队列/I2S/音量，再查声学。
- **网络的判据**：校验值大量缺失或乱序、下行欠载（underrun）成段出现、MQTT EOF/重连与故障时间重合。
- **业务状态的判据**：媒体帧都正常，但会话 phase/错误码异常（如 `phase=8 error=-40008`），或命令被判无效。
- **板端正常、手机异常的判据**：板端采集、编码、发送计数都在走，错误为 0 → 先排除现场条件（镜头被挡、手机页面、账号授权），再查码流。
- **内存的判据**：多轮回到空闲、最后一轮后静置 130 秒（TCP 控制块要约 2 分钟才释放），free 仍持续下降（斜率 < −256 B/轮），而不是只看一次最低水位。长时间待机监测（`xt.py watch`）要找“台阶”：一步掉下去以后又平了，就把台阶和同一时刻的事件（断线重连、某次通话、提示音）对上，再用那个事件重复多次，看每次是不是都掉。只看整体斜率会把一次性的台阶误判成持续泄漏。

## 第三步：改之前的硬规则

1. **先取证再改**：一次只改一个变量，用同一条命令复测，对比 `summary.json`。修之前先写一个能复现的主机夹具，原代码上红、修后变绿；台架上偶发的问题尤其要这样，否则修没修好说不清。复现不了的偶发问题，先加“出现那一刻的取证”和“有计数的自动恢复”，再去做别的（[案例 22](references/案例.md#22-相机偶尔不出首帧没定根因时怎么收口)）。同一类问题修两轮还不过：记下现象、已排除的原因、下一步猜测，先做别的。
2. **回声/噪声处理的改动必须先过仿真**：`sdk/xiaotai_media/test/echo_gate_test.c` 里的两机互呼防啸叫仿真（共振峰 +4/+10/+16 dB、音量 40/100）不过，不许上板。
3. **用真实数据调参**：门限、时间常数先用 `trace.json` 里的真实电平离线回放，再写进固件。
4. **区分“状态”和“缺陷”**：保存的偏好（如闭麦）、保存的旧网络、两端固件不是同一代（先 `AT+VERSION`）、用户操作、测试摆放（两台设备互相能听到）都可能造成“像 bug”的现象，先排除。判断“设备没有某个功能、某个指令”之前，先查源码。
5. **打开串口不能复位设备**：先置 DTR/RTS 为 False 再 open；pyserial 默认 open 会复位 ESP32 USB-JTAG 板。
6. **烧录**：先按 `xiaotai-build` 第 6 节读分区表定写几段；只写 APP 时用 `xt.py flash DEV <bin>`（默认 0x10000）。看到 `Hash of data verified` 即可，不做整片擦除。

## 常用判例

[判例](references/案例.md)开头有一句话索引。最常碰到的几条：

- 开机反复重启、回溯停在存储或分区映射：栈在外部内存的任务碰了 Flash（判例 11）。
- 多轮后少一两 KB：TCP 控制块要两分钟才释放，静置后再比（判例 14）。
- 板端发帧正常、手机黑屏：先看亮度，可能镜头被挡（判例 17）。
- 某个器件开机打不开、旧固件没问题：共用电源轨或复位被别的零件先动了，逐条比旧板级初始化（判例 18）。
- 不敢烧录：读 `0x8000` 起 3 KB 的分区表就知道旧布局（判例 21）。

## 交付要求

每次定界结论写成：固件（板型、ELF 前 8 位、台架版还是默认版）→ 现象 → 命令 → 关键数（贴 `summary.json` 片段）→ 判定层和已排除的原因 → 修改 → 复测数。没证实的写“未证实”加下一步，不写成通过。日志里的 Wi-Fi 密码、令牌、绑定码、设备号去掉再给别人看。新的判例补进 [案例](references/案例.md)（现象、定位命令、根因、办法、以后怎么一眼认出），新的命令补进 `tools/xt/README.md`。
