# 定界方法

每节写清：怎么取证（命令）、看哪些观察量、怎么判到哪一层。命令都在 `tools/xt/xt.py`。

## 设备与观察量总览

各产品用同一套统一 SDK 指令，一台设备实际有哪些以 `AT+HELP` 和本次构建的 `commands.json` 为准：

| 用途 | 指令 | 看什么 |
| --- | --- | --- |
| 版本 | `AT+VERSION` | `+BUILD` 行的完整 ELF；两端先核对是同一代固件 |
| 通话 | `AT+CALL DEVICE <设备号>`、`AT+CALL INDEX <n>`、`AT+CALL ACCEPT/REJECT/HANGUP`、`AT+CALL MUTE 0/1`；`AT+CALL` 读状态 | `+CALL: kind=… state=… gen=… end=…`（`end=1` 本端挂、`end=2` 对端挂） |
| AI | `AT+AI START/STOP/INTERRUPT`；`AT+AI` 读状态 | 会话阶段和结束原因 |
| 界面 | `AT+UI TAP x y`、`AT+KEY CLICK/DOUBLE/HOLD`；`AT+SCREEN` 截图 | 页面和按钮意图 |
| 传输 | `AT+LINK` | `+LINK-MEDIA` 的 tx/rx/丢弃，是开机以来的累计值，xt 取通话前后的差 |
| 媒体 | `AT+STATUS media` | 采集电平、`deadline_misses`，播放的欠载和 `pcm_written` |
| 网络和平台 | `AT+NET`、`AT+PLATFORM`、`AT+STATE` | 在线、授权、信令；重连次数和运行时长 |
| 内存 | `AT+MEM` | 内部和外部 RAM 的空闲、最大块、最低水位 |

逐帧抓包：`AT+TRACE ARM [帧数] | DUMP | OFF`。每帧 12 字节记在 RAM，通话中不打印，不影响音频。

## 音频通话

**一条命令：** `xt.py trace A B -s 18 --frames 1000`（无 PSRAM 的板内存紧，单向最多 1000 帧≈20 s）。

报告字段与判定：

| 字段 | 含义 | 判定 |
| --- | --- | --- |
| `A->B.matched / sent` | A 发出的帧在 B 播放端按 FNV 校验值找到的比例 | ≥98% 且缺的只在首尾 → **传输/网络正常** |
| `A->B.sender_state` | A 发送时回声门/噪声门状态分布 | 说话期间大量 closed/attenuated → **A 端处理压掉了** |
| `level_db_mic_median` vs `level_db_sent_median` | A 麦克风电平 vs 实际发送电平 | 麦克风高、发送低 → 处理层；麦克风本身低 → 声学/驱动/增益 |
| `peer_gate_open_frames` | 对端上行门打开的帧数 | A 说话时对端门大量打开且对端没在播放 → 对端房间有声音（含串音），半双工端会被压 |
| `underruns` | 接收端没有帧可播 | 成段出现 → 网络抖动/欠载 |

逐帧对齐：`trace.json` 里两端 TX/RX 同序号附近对比（脚本见案例 3）。

**声学耦合实测**：只放远端声音、本端不说话时，本端麦克风电平 − 本端播放电平 ≈ 喇叭到麦克风的耦合。C3 单键板音量 80/增益 36 实测约 +13~16 dB（模型按 +38 dB 设计，偏保守，为窄带共振留余量，见案例 5）。

## AI 会话

- `xt.py ai DEV -s 60`：看 `rx_dropped`/`rx_drop_pct`、`samples` 中每 10 s 的收发、结束后是否回空闲、堆最低水位。
- `xt.py ai-keys DEV`：按真实按键流程（首页双击开始 → 单击打断 → 长按结束），核对 `AI interrupt sent ... error=0`。
- 判定：
  - 下行丢帧集中在 AI 回答开头 → 服务端突发下发快于实时，接收队列太小（无 PSRAM 板的下行队列 8 帧=160 ms）。属于**设备接收缓冲**，不是网络丢包。
  - 回复中途结束且日志有 `MQTT error`/`transport_read(): EOF` → **平台连接断开**导致会话被结束。
  - 上行帧数正常但服务端无响应 → 需服务侧时间线，不能凭设备侧断定。

## 微信通话

- `xt.py wx-in DEV`：手机点设备卡片“微信通话”，设备串口接听。`xt.py wx-out DEV --phone-hangup`：设备呼手机，手机点接听、通话后由手机挂断。
- 手机端操作前先截屏读关键像素判断所在页面，不在设备列表就从微信下拉“常用的小程序”重新进入；会关闭遮挡按钮的服务通知浮窗。坐标在 `devices.json` 的 `phone` 段，换手机或列表顺序变化要重新量。
- 判定：设备 tx 为 0 → 查该设备 `uplink gated` 原因（会话/链路/闭麦）；挂断后设备不回空闲 → 查挂断信令载荷兼容（案例 2）。

## 网络与平台

- 掉线先区分：Wi-Fi 断（`Wi-Fi: disconnected`、无 IP）、MQTT 断（`MQTT error`、EOF、平台 epoch 递增）、HTTP 失败（`thing_http: done: http=... code=...`）。
- 业务码先查含义再下结论：`40201` = 被叫全部离线（不是本机故障）。
- 长时监测：`xt.py log DEV -s 600 > ...`，统计 MQTT 断开次数和间隔，与 Wi-Fi RSSI、服务端时间对齐。

## 内存

**一条命令：** `xt.py soak DEV --rounds 15 -s 6`（多轮 AI，前后各静置至少 130 秒，核对同一固件、同一次启动后比较空闲内存）。`--peer` 只对旧固件有效；通话路径连续跑几次 `xt.py call`，比较前后的 `AT+MEM`。

| 观察量 | 含义 | 判定 |
| --- | --- | --- |
| `free_bytes_per_round` | 空闲 free 的线性斜率 | < −256 B/轮 → 疑似泄漏，需继续缩小到功能（只跑 AI 或只跑通话） |
| `largest` | 最大连续空闲块 | 第一轮后下降然后稳定 → 碎片或常驻缓存；持续下降 → 碎片化加剧 |
| `minimum` | 历史最低水位 | 只说明最危险时刻余量，不能单独判泄漏 |

缩小范围：分别跑“只 AI”“只通话”“只微信”，看哪种功能让斜率为负；再在该功能的开始/结束点前后打印 free，定位未释放的分配。

## 回归清单

一次完整回归（两块设备 + 手机；每条都带两端的词表、ELF 和逐条授权，见 `xiaotai-test` 第 4 节）：

```text
xt.py gate A ...          xt.py gate B ...
xt.py call A B -s 10      xt.py call B A -s 10
xt.py wx-in A             xt.py wx-out A
xt.py wx-in B             xt.py wx-out B
xt.py ai-keys A
xt.py trace A B -s 10     (无人说话：门控应全关、匹配率 ≥98%)
xt.py soak A --rounds 10
```

全部 `pass` 再进入真人听感确认。真人只确认“听感”，计数和状态全部由命令给出。
