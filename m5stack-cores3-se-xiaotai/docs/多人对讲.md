## 设备操作

入口为“更多功能 → 多人对讲”。设备先联网并完成绑定。

1. 打开应用时查询本机房间归属。没有房间时显示“创建房间”和“加入房间”；已有房间时直接连接该房间。
2. 创建房间的密码可留空或填写四位数字；加入时输入六位房间号，保留开头的零。
3. 状态显示“收听中”后，按住底部按钮讲话，松开停止发送。
4. 右上角“退出房间”删除本机入房关系，成功后回到创建/加入选择。
5. 左上角返回菜单只关闭房间应用：停止收发、断开 RTC、释放租约，保留房间归属。
   离页后不轮询、不续租、不自动重连；再次打开应用才重新查询并连接。开机也不会后台自动入房。

界面按 320×240 布局，不缩放 P4 截图：44 px 顶栏、固定房间号、三行成员、翻页和 44 px 讲话按钮。
房间表单使用独立四列三行数字键盘：`1 2 3 4 / 5 6 7 8 / 9 0 退格 确认`，
每键约 72×48 px；点击输入框切换焦点，退格支持长按，确认松手提交，不改其他页面键盘。
本机显示服务端设备名称，未命名显示设备 ID，后接“（本机）”；标记单独保留，长名称省略时也不会丢失。
其他成员优先显示已有普通联系人的备注名，没有备注显示设备 ID，不使用固定“小钛”名称。
当前公开 Room 协议仅保证 ID，不保证下发名称。本机名称按可选 `device_name` 读取，来源为
assignment、room_snapshot.self 或 participants 中的本机对象；缺字段时保留已知名称，明确空字符串则清除。
部署端实际字段和网页改名推送仍待用户日志核对，不能把接口扩展支持写成已完成云端联调。
只展示当前成员快照，不伪造离线成员或在线状态。密码错误、房间关闭、容量限制和旧租约冲突有独立提示。

## 实现边界

| 分层 | 实现 |
| --- | --- |
| 页面 | [starter_product_s3_room.inc](../components/starter_product/src/starter_product_s3_room.inc)，LVGL 任务只投递意图、读取三行快照 |
| 房间状态 | [starter_room.inc](../components/starter_runtime/src/starter_room.inc)，复用现有 runtime 任务，单一所有者串行处理 |
| 平台接口 | 复用现有 HTTP 工作任务和正式设备鉴权，调用 assignment/create/join/leave/connect-token/presence |
| 传输 | [starter_tirtc.c](../components/starter_tirtc/src/starter_tirtc.c)，新增 Room 模式，仍只占用一路 RTC |
| 音频 | 复用现有单麦 AFE（AEC + NLP）、AGC、G711A 和自适应播放；新增按住发送门控，不更改算法参数 |

收到 HTTP 成功只表示关系已保存。完成 WHIP、发送 `0x2200 join_room`、验证确认中的上下行格式后，才启动媒体。
上下行固定为 **G711A / 8000 Hz / 单声道 / 20 ms / stream 1**；协商不符直接报错，不按错误格式播放。
同时发言的混音由服务端完成，设备只处理一条下行混合音轨。

PTT 松手或触摸移出时，按采集时间只放行松手前已采集的帧，最多排空 600 ms，避免截掉最后一个字；
松手后采集的帧不发送。按下、麦克风静音、页面销毁、断线、代次变化及业务抢占立即截止。
关闭不等待 HTTP 或 runtime 队列；快速松开再按也不能复用旧帧。已经进入 SDK 的单次发送无法撤回。
`ROOM CAP` 日志的 `drain=` 为松手后按采集时间放行的帧数，`ring=` 为 AFE 环满丢块数。
`set_mic_state` 仅同步状态，不替代本机音频门控；本机发言显示以本地状态为准。

AI、微信和设备通话优先于房间。页面转到其他应用即关闭房间应用，不在其他通话结束后后台抢回 RTC。
如果应用仍在房间页面，只是临时被业务占用，则等所有者释放后重新同步；真正离页必须重新打开才恢复。
关闭使用 `leave_room` + RTC disconnect，并以 `presence.state=left` 释放本次租约；
HTTP `device/leave` 只用于用户明确点击“退出房间”。两种操作不能混用。
复用的 HTTP/MQTT、音频/唤醒及 runtime 任务不会被删除。关闭前已经提交的 HTTP 允许有界完成；
旧读取/凭证回调按票据失效，已提交的创建/加入/退出只接收一次最终结果，不启动新的后台连接。
应用开关有独立原子版本，关闭立即禁止 PTT，runtime 负责有序清理；快速关闭再打开也不能复用旧连接。
HTTP 请求票据、绑定代次、关系版本、业务会话、RTC 代次分别校验；重复通知合并，读请求期间的新通知不会被旧响应覆盖。
租约使用服务端返回的间隔，并以请求发出时间计算保守截止点，不把 HTTP 耗时或入房耗时额外加进租期。
元数据或续租暂时失败不会立即切断仍有效的音频，但不能延长旧租约；到期或服务端明确拒绝则停止。

当前一次故障最多自动重建三次；`40921` 按租约时长等待后再试。持续失败保留错误，用户刷新或网络重新上线可重新尝试。
本轮没有扩展房间内声学唤醒。返回菜单释放房间 RTC 后，AI、微信、设备互呼、H5 可按原路径使用，
无需删除持久房间关系。未调整 SDK、AEC、增益、编解码或播放参数。

## 内存

未新增任务、任务栈、信号量、音频池或 NVS 字段；SDK 与 sdkconfig/defaults 保持本轮开始时的版本和配置。

下表为此前已构建候选的符号证据，不覆盖本次前台生命周期/名称调整。

| 原候选新增对象 | 位置与大小 |
| --- | --- |
| 房间所有者模型 | 外部 BSS，16,784 B |
| 发布给 UI 的成员快照 | 外部 BSS，16,928 B |
| Room 页面状态 | 外部 BSS，616 B |
| 三个原子控制量 | 内部 BSS，共 12 B |
| 房间私有 JSON 解析器控制量 | 内部数据/BSS，共 20 B；堆节点、字符串及扩容显式 PSRAM，不回退内部 RAM |
| RTC 信令副本 | 按实际长度在 PSRAM 申请，单条最多 32,768 B，消费后释放 |

原候选前三项共 34,328 B PSRAM；内部固定控制量共 32 B。本次增加两个原子版本字段（S3 共 8 B 内部 RAM）；
本机名称和 UI 指针等留在现有外部 BSS，不为 100 个成员各分配一份名称。新布局的完整大小待再次构建确认，
不得继续以旧 ELF 数字宣称当前资源水位；LVGL 新增本机标记对象也需要重新测量池峰值。
JSON 使用锁定依赖中的 cJSON 源码进行私有符号编译，限制嵌套深度 12；没有修改全局 hooks、SDK 或第三方源码。
这是为避免百人成员解析时大量小节点落入内部 RAM，不能改回普通 `cJSON_Parse` 或临时切换全局 hooks。

## S3 对 S3 断续排查

用户反馈：多人对讲时，另一块 S3 听到语音断续。本轮没有该次通话的双端时序日志，**根因未证实**。
本轮只补诊断，不调整 AEC、增益、编码、队列容量、变速参数、SDK 或配置，不以“增大缓冲”代替定位。

| 节点 | 当前源码事实 | 仍需验证 |
| --- | --- | --- |
| 采集 | 所有模式共用 ES7210 四槽输入，取 MIC1/MIC3 重排为 MR（MIC2 只统计电平）；同一 ESP-SR 单麦 AFE/AEC、AGC，处理输出保持 16 kHz | 输入队列满、处理超时、代次丢弃是否发生在断续时刻 |
| 上传 | CoreS3-Lite 与 AI 使用同一 PCM 队列，16 kHz PCM 经抗混叠降采样到 8 kHz，再以 G711A 单声道发送；每包 20 ms / 160 B，时间戳递增 20 ms，流 1 | DSP 按块输出后可能连续提交多个小包，实际发送间隔并非固定 20 ms；服务器是否能吸收该突发需两端日志 |
| 业务差异 | Room 有 PTT 门控，无 AI 唤醒预录回放；Room 经过服务端混音，接收端不能逐包对比原上传校验和 | 本机按钮连续按住期间门控是否反复变化，混音前后是否缺帧/补静音 |
| 接收播放 | 共用 PSRAM 入队、解码、跨包 PCM、自适应缓冲、微幅调速、I2S 输出锁、连续插值和重启淡入 | 到包已断续，还是本地消费/锁等待导致输出断续 |

“用了同一套播放代码”不等于每项策略都已生效：当前变速需至少八个连续时间戳并预热两秒；
恒定/跳变时间戳会禁用变速。自适应抖动估计也会跳过部分不连续时间戳，需检查 Room 下发数据。
缓冲目标为 200 ms 起步、60–500 ms；319/320/321 样本微调约 0.3125%，用于缓慢平衡水位，不能补回丢失人声。

### 本轮诊断与复现

Room 活跃时由 runtime 每五秒输出四条摘要；采集、发送、接收回调只更新计数，不逐包打印。
新增固定诊断对象为 132 B PSRAM（S3 编译期断言），无新任务、队列或内部 RAM 全局对象；实际耗时和栈峰值尚未实测。

| 日志 | 重点字段 |
| --- | --- |
| `ROOM CAP` | `ptt` 当前门控；`calls` 接受的按下/释放调用次数，不是物理触摸次数；`full/timeout/stale` 定位采集丢弃 |
| `ROOM TX` | `in/full/stale/sent/err_gain/enc/send` 分离入队、队满、门控过期、SDK 接纳和错误；`sent` 不等于对端收到 |
| `ROOM RX` | 字节/帧数、实际回调间隔、时间戳重复/前跳/后退；`burst5/gap60` 只表示小于 5 ms/大于 60 ms 的间隔 |
| `ROOM PLAY` | 缓冲目标/水位、重新预缓冲次数、时间戳连续性、队满/过期、静音阻断、解码/写入失败、锁超时、服务间隔、源 PCM 消费守恒、变速次数 |

Room 新计数为开机累计，比较同一窗口差值；共享采集/播放计数及最大值可能包括此前其他会话。
`t` 是本机启动毫秒，两机不可直接相减；播放 `starts/late` 随媒体代次重置。
接收空档也可能是无人讲话或服务端停发，PTS 跳跃也可能是时钟重置，不直接换算丢包率。
`obs_skip` 非零表示时序观测遇到并发、回调执行先后与入口计时不一致，或间隔超过约 35 分钟的计时范围。
跳过的仅是统计，不阻塞或丢弃媒体；该区间不能按完整连续采样解释。实际媒体仍按原有队列逻辑处理。

复现按 A 持续按住讲话 30 秒、B 收听，再交换方向；记录两端同一轮日志与用户听到断续的位置。
先用普通 Wi-Fi，不注入弱网；之后再单独增加延迟、抖动、丢包，避免同时改变多个变量。
在稳定按住区间比较发送吞吐与接收音频时长；共享采集正常且发送连续、接收突发时，进一步要服务端混音与传输日志。
接收连续但本地水位/写入异常时，才修改本地播放责任层。音频数据本身已有静音孔洞时，仅看包数不能排除问题。

旧私有 `room-hil/probe.c` 的定时 PTT 每 40 ms 重复提交按下，而当前媒体按下会增加 mute epoch、清理拼包/AGC 残留。
该测试方式会主动污染连续性，不可拿旧脚本的听感/包数作为本次根因证据；后续脚本须一次按下、到时一次释放。
当前手动 UI 只在 `LV_EVENT_PRESSED` 请求按下，暂不能用脚本问题解释手动卡顿；本轮未更改 PTT 语义。

已补充 RX 观测不改变 AI 接收/顺序/载荷的用例，以及 SDK 白名单与敏感信息隔离用例；尚未运行主机回归、编译或烧录。
