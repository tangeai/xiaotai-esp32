# 系统与媒体架构

本文介绍小钛 P4 的代码分工和媒体流程，供修改功能、调参数和定位问题时查阅。构建输入见[版本与依赖](DEPENDENCIES.md)。

## 代码分工

| 模块 | 负责什么 |
| --- | --- |
| `main/xiaotai_main.c` | 初始化 NVS、媒体、UI、Wi-Fi，启动后台上线流程 |
| `platform_client` / `runtime_config` / `wifi_manager` | 平台请求、身份保存、配网及 C6 Wi-Fi 接口 |
| `nvs_store` | 公共异步读写队列、完成结果和内部 RAM 存储任务 |
| `starter_runtime` | 协调 AI、设备呼叫、微信、多人对讲和 H5 会话，处理取消、挂断与事件 |
| `starter_tirtc` | SDK 初始化、连接、回调、订阅和媒体发送 |
| `starter_product` | LVGL 页面、字幕、表情及用户操作 |
| `starter_voice` | 从处理后的 PCM 识别唤醒词 |
| `starter_media` | I2S、AEC、增益、预录、音频发送与播放 |
| `p4_hardware` | 摄像头、编解码、视频显示、码率调节及板级接口 |

业务和驱动通过各自队列传递事件。耗时网络请求不在 LVGL 锁中执行，音频采集也不直接调用 SDK。

`main/xiaotai_main.c` 是唯一应用入口；`p4_hardware` 引用 `main/` 中的硬件、摄像头、编解码和显示模块，具体范围见 [p4_hardware/CMakeLists.txt](../components/p4_hardware/CMakeLists.txt)。旧 Monitor 的启动、界面和业务副本已移除。当前页面、表情和 P4 视频通话页均由 `starter_product` 管理。

## 启动与绑定

启动依次初始化 NVS、媒体、UI 和 Wi-Fi，再由后台等待联网、校时、绑定及 TiRTC 就绪。DSP 和媒体池准备完成后才启动 ADC/DAC 与采集任务。

已保存凭证与首次绑定共用校时入口：Wi-Fi 获得 IP 后，必须收到本次开机的 SNTP 同步结果且时间有效，才允许服务发现、设备上报/鉴权和 TiRTC 初始化。复位后保留的日期不能单独作为放行依据；校时成功后复用结果，SNTP 在后台继续刷新。保持 TiRTC 先于永久 MQTT 启动的内存顺序，不提前创建 MQTT 大栈。

校时等待在现有后台上线任务执行，不占用 LVGL 或音频采集任务。单次等待覆盖已配置 SNTP 服务器的超时窗口；失败记录原因，5 秒后在联网条件下继续等候同一 SNTP 服务，不执行后续上线动作，也不反复初始化校时资源。

六位码在临时 MQTT 订阅就绪后展示，不等待提示音结束。页面同时显示 `https://xiaotai.chat/`，引导用户打开网站并输入验证码；此网址仅用于用户配置入口，不替换服务发现或 API 地址。HTTP/MQTT 结果带身份代次，用于识别解绑前的旧响应；解绑由平台模块完成身份转换和持久化。

配网和绑定页面由现有 100 ms UI 定时器直接读取网络、绑定状态，先于业务快照刷新；热点名称、网址和操作结果每秒更新。首次绑定完成前业务快照互斥量尚未创建，不能用获取快照失败作为整个 UI 的返回条件。页面构建也不读取业务快照，避免解绑或断网时等待通话快照锁；恢复绑定后再进入正常业务页面。不新增任务或常驻缓存。

UI 读取缓存的 Wi-Fi 状态，C6 RSSI 查询在绘图锁之外执行。视频呈现与业务页面分开刷新，表情只更新受影响的区域。

### 平台 HTTP 连接

服务发现、签名登录和验证码绑定保持一次性连接，避免等待用户操作时占住 socket。上线后由唯一 HTTP worker 串行处理业务请求；同协议、主机和端口的成功请求可短暂复用一个连接，减少 AI token、资料上报和联系人查询的重复握手。复用状态占 264 字节 PSRAM；不新增任务，SDK/TCP 连接本身仍有临时内存开销。

每次请求后清除签名、Authorization、POST 数据及调用者指针。空闲超过 3 秒后不再复用，worker 最迟在下一次空闲检查时释放；跨站请求、失败、重定向和解绑也释放。服务端关闭连接时保留失败语义，不自动重发可能已执行的 POST。此优化不提前放行校时、鉴权或媒体状态。

### 设备能力上报

永久 MQTT 上线且 HTTP worker 就绪后，`starter_runtime` 异步提交一次 `POST /v1/device/profile`，使用 `device-srv` 和正式 `mqtt_token`。这替代已弃用的微信 profile 接口，不额外创建任务、连接或上报链路。请求体不含设备 ID、密钥或临时 token。

一个请求完整携带三个场景的快照，不能按字段拆开覆盖：

| 场景 | 音频上行 / 下行 | 视频上行 / 下行 |
| --- | --- | --- |
| `stream` 实时查看 | A-law，8 kHz，单声道 | H.264 / H.264 |
| `call` 设备通话 | A-law，8 kHz，单声道 | H.264 / H.264 |
| `voip` 微信通话 | A-law，8 kHz，单声道 | H.264 / MJPEG |

三类场景均完整上报其适用字段：`stream` 16 项、`call` 12 项、`voip` 16 项。除上表中的编码、采样率与声道数，画面参数如下：

| 参数 | 实时查看 `stream` | 设备通话 `call` | 微信通话 `voip` |
| --- | --- | --- | --- |
| 上行宽高比 `aspect_ratio` | 0.75（960×1280） | 1.5（384×256） | 0.75（960×1280） |
| 呈现旋转 `camera_rotation` | 0° | 0° | 270°，保持原微信界面校正 |
| 水平 / 垂直镜像 | 均为 `false` | 均为 `false` | 均为 `false` |
| 画面适配 `object_fit` | `contain` | `contain` | `contain` |
| 无视频 `no_video` | `false` | `false` | `false` |
| 显示区域宽 / 高 | 接口不适用 | 接口不适用 | 480×320 |
| 下行编码方向 `down_video_rotation` | 接口不适用 | 接口不适用 | `0`，沿用上游默认方向 |
| 下行尺寸模式 `video_res_mode` | 接口不适用 | 接口不适用 | `auto`，沿用透传尺寸策略 |
| 呼叫超时 `calling_timeout_sec` | 接口不适用 | 接口不适用 | 30 秒 |

宽高比取自 [media_tuning.h](../main/media/media_tuning.h) 的当前编码尺寸。实时查看复用微信竖屏编码配置，在编码前已完成摄像头方向校正；`camera_rotation=0` 表示不要求接收端再次旋转。上报字段描述的是呈现约定，不修改 PPA、采集、AEC、编解码或本地播放。微信保留现有参数，仅将默认下行方向与尺寸策略写明；`auto` 与原来不传此字段等价，见[微信下行尺寸模式](https://docs.tange.ai/products/wxvoip/api-reference/server-api.html#下行视频分辨率模式)。后续微信通话会读取本快照，调整参数时仍须回归双向视频。

能力以当前产品收发路径为准，不列入 SDK 中尚未接通本业务的编码。接口未定义 `voip.up_audio_mt`，也不接受 AI / 多人对讲场景、固件版本、CPU、RAM、RSSI 等自定义字段。`has_camera`、`has_screen`、`voip_room_type` 由服务端从微信能力推导，设备不能回传这些只读字段。

HTTP 200 且业务 `code=200` 才开放微信通话。AI、H5、首页及联系人查询不依赖上报成功。暂态失败或响应事件丢失间隔 15 秒重试，每轮上线最多尝试 3 次；参数或鉴权错误停止本轮重试并保留错误。HTTP 410 / `6006` 进入现有解绑核对流程。MQTT 重连或重绑后重新上报，旧身份的迟到响应丢弃，同一时刻最多一笔在途请求。

请求常量放在只读区，发送副本复用现有 2048-byte PSRAM 请求槽，上报状态也在 PSRAM。成功后可在平台“我的设备 → 更多 → 设备信息”核对。接口字段与替换语义见[上报设备能力](https://github.com/tangeai/tirtc-server-example/blob/main/thing-connect/api-reference.md#post-v1deviceprofile)。

### 实时查看的订阅方向

`stream` 能力中的上下行以设备为参照，流号标识发送端的流：

| 方向 | 音频 | 视频 | 发送条件 |
| --- | --- | --- | --- |
| 设备发送，网页接收 | `up_audio_streamid=10` | `up_video_streamid=11` | 网页订阅对应流后设备才发送，取消订阅即停止 |
| 网页发送，设备接收 | `down_audio_streamid=14` | `down_video_streamid=15` | 设备接收链路就绪后分别订阅 14/15，网页再按对讲操作发送 |

会话任务在音频播放就绪后提交音频 14 的订阅；P4 视频 owner 在 H264 解码器就绪后提交视频 15 的订阅。两项接收许可分别绑定当前连接代次，SDK 可能在订阅调用返回前同步送达首帧，因此适配层先登记代次再调用 SDK，失败时只撤销同一代次。断开或换代会同时清除接收许可，迟到帧按连接、代次、流号和编码过滤。订阅对端 14/15 不会开启本机 10/11 上传；本机上传仍由网页对 10/11 的订阅回调独立控制。P4 实时查看上报并接收 `down_video_mt=["h264"]`。

以上规则仅用于 H5 实时查看。AI、设备呼叫、微信和多人对讲保留各自的业务握手与流号约定，不能套用 H5 的流号过滤。

## 表情动画

首页与预览页使用同一个公式光栅化绘制器，提供 23 种表情：“思考”“放松”固定使用第一套姿态及动作，其余 21 种随机二选一，共 44 个可用姿态和动作片段。AI 思考阶段也固定第一套。保留前 21 项编号，“聆听”“悠闲”追加在末尾；旧 `speech` 输入映射为 `listening`。

同一表情重复下发只更新活动强度，不重新选择姿态或启动动作。切换表情时先计算当前过渡姿态，再以它为下一段起点；动作结束后归回基础姿态，继续轻微呼吸、视线和眨眼。AI 聆听、思考阶段优先使用状态表情，避免上一情绪的装饰混入。

绘制仍由单个 40 ms LVGL 定时器驱动，隐藏或休屏时暂停；状态和画布在 PSRAM，不逐帧申请内存。最多记录 96 个图形边界，按三块区域合并旧、新位置，并按 P4 图像缩放换算刷新坐标；边界槽溢出时下一帧全清，避免残影。基础轮廓保留 RGB565 字节序处理，彩色装饰单独叠加。

B 套采用宽厚弯豆/折叠眼、浅波浪嘴及双瓣亲亲嘴，轮廓参数随切换插值；墨镜、双泪滴、腮红和 zzz 按各自含义绘制，放松的哼歌音符保留第一套。B 套眨眼闭合侧保留 24 像素厚度。聆听与思考阶段使用阶段自身的轮廓扩展，避免继承上一情绪的折叠眼或嘴形装饰。

自然眨眼按眼高和折叠强度连续混合，避免切入折叠眼时突然撑开。每次进入新表情重置该表情的提示动作时钟，即使旧装饰仍在淡出；重复活动更新或保持同一表情的阶段切换不重播。

代码：[表情绘制器](../components/starter_product/src/starter_product_s3_face.inc)。文件名沿用已有命名，实际文件位于本 P4 工程，不引用 S3 源码。

## 多人对讲

沿用现有 runtime 和 HTTP worker，不另建一套会话任务。平台的房间归属、TiRTC 连接成功和 `join_room` 应答分别处理；只有应答确认了会话与音频格式，才允许媒体收发。默认收听，按住按钮才发送 G.711A / 8 kHz / 单声道音频。

- 房间归属通过 HTTP 查询或修改；成员快照与麦克风状态通过房间 JSON-RPC 命令通道处理。修改成功的回执不直接当作最新成员列表。
- 页面读取非阻塞快照，每次显示 3 位成员。成员表和快照放在 PSRAM，固定上限 100 位；解析和消息大小有界，不随服务端列表无限扩容。
- PTT 绑定连接代次。松手、失去触摸、离开页面、麦克风静音或连接结束立即撤销发送许可；重连不会自动恢复上一次按住状态。
- 退出旧连接时保存房间 ID、关系版本和会话 ID，联网后先上报旧会话释放，再申请新连接。`200` 才计为释放确认；旧代次或房间已关闭的返回只说明该事务已过时，随后重新查询归属。
- 多人对讲只在自己的房间页或输入页打开时工作。UI 导航发布前台开关，runtime 负责关闭属于 ROOM 的媒体连接；不停止共享 RTC 监听、永久 MQTT 或其他应用会话。开关带导航代次，快速返回再进入也必须释放旧连接。
- 返回菜单保留房间关系，停止 PTT、收听、心跳、成员刷新和自动重连；已提交的释放事务或用户明确要求的退房事务仍完成收尾。再次进入先核对最新关系，再申请新连接。右上角“退出房间”调用持久 `leave` 接口，与返回时的 `presence/suspended` 不同。
- 成员快照中本机的可选 `device_name` 用于显示平台名称；空字符串清除旧名称，字段缺失时保留当前身份已获名称，否则回退设备 ID。其他设备使用通讯录备注或设备 ID。“（本机）”单独绘制，长名称省略时标记仍可见。

上述释放事务保存在易失性的 PSRAM，断电后不会保留；这时仍需按服务端租约处理。不能把可恢复的断网退出和突然断电视为同一种完成保证。

代码：[房间状态机](../components/starter_runtime/src/starter_room.inc)、[房间页面](../components/starter_product/src/starter_product_room.inc)。

## NVS 与信令常驻

应用读写统一走 [nvs_store](../components/nvs_store/include/nvs_store.h)。启动时先初始化 NVS 分区，再启动唯一存储任务。`nvs_get_*` 同样可能触发 Flash 关缓存，不能在 PSRAM 任务中直接读取。

- `nvs_store_submit` 复制参数后立即返回票据；入队成功不代表保存完成。调用方用 `take_result` 获取真实结果，或 `abandon` 放弃接收结果。
- `read_async` 提交单键读取，`take_read_result` 在完成后复制结果；不会将调用方输出指针交给后台。启动加载使用有界等待接口 `read`，仍由内部存储任务执行。
- UI 最多保留一个在途票据和一份最新设置，快速连续操作会合并尚未提交的值。每次写入使用独立快照，不读取正在变化的 UI 状态。
- 配网和绑定使用 `execute`，由同一 worker 写入，调用方最多等待 5 秒；只有保存成功才继续流程。超时不撤销已接受的写入，也不会触发自动重试。
- 池固定 8 槽，写入每批最多 8 项，读取每批一个键；数据最多 512 bytes。排队及待读取结果位于 PSRAM，worker 使用 3072-byte 内部栈和 728-byte 内部暂存区；同步控制块另算。
- 保持现有 NVS 键和 Wi-Fi 单 blob 格式。多键保存并非原子事务，错误不能解释为数据已经回滚。队列满、写入失败和栈水位不足都会保留错误信息。

异步接口减少业务任务的阻塞和内部栈需求，但不消除 Flash 操作本身的短时关缓存。其他任务是否能迁到 PSRAM，仍须检查其完整调用链，不能只看是否移除了 NVS 写入。

音量与扬声器静音也使用非阻塞请求，但不由 NVS 任务操作硬件。现有音频输出任务在空闲时、或当前播放者在 PCM 块边界应用最新值；验证码和铃声每块 20 ms，仍保持完整的播放互斥。这样播报不会让 UI 等待扬声器锁。`starter_media_status()` 分开提供请求值、已应用值和硬件错误；硬件失败会记录错误并提示，不与保存成功混为一谈，也不自行无限重试。

永久 MQTT 由平台身份生命周期管理。AI、普通呼叫、微信和多人对讲建连时，只归还预留的 17 KiB 连续内部块，不停止 MQTT；接听、挂断、解绑及成员变动仍通过原信令通道接收。后续预留块申请失败不阻断当前信令和媒体，但下一次建连仍须取得所需内存。

## 音频采集

```text
ES8311：MIC 槽 0 + DAC 回采参考槽 1
    -> I2S1，16 kHz / 16 bit / 双声道同步读取
    -> ESP-SR MR 回声消除
    -> 约 100 Hz 高通 -> 数字自动增益
    ├─ 16 kHz PCM -> 唤醒识别
    └─ 抗混叠降采样至 8 kHz -> 预录 / 实时队列
        -> rtc_audio_tx：标称 +9.52 dB 带限幅增益（原 6 dB 的 1.5 倍幅度）
        -> G.711 A-law，20 ms 分包 -> TiRTC
```

这里的双声道是“一路麦克风 + 一路参考”，硬件只有一个物理麦克风。参考用于告诉 AEC 扬声器正在播放什么。

| 处理 | 当前配置与修改要点 |
| --- | --- |
| AEC | 16 kHz，`mic_num=1`、`ref_num=1`、`FD_LOW_COST`、`NLP AGGR`、`filter_length=4`；处理块大小从库查询 |
| 高通 | 极点 `31506/32768`，保留跨帧状态，只处理 AEC 输出 |
| AGC | 自动调节 AEC 后的人声电平；参考信号不参与增益 |
| 上传增益 | 在发送任务中施加一次，覆盖实时和预录；相对原值标称放大 1.5 倍，保留 -3 dBFS 限幅目标，不再次放大唤醒输入 |
| 预录 | 带会话代次和中断状态，网络发送与 I2S 采集分开 |

AEC 随采集初始化，调节应落在 `starter_media` 中。检查连续性时记录 I2S 溢出、处理耗时、预录缺口和发送丢弃，再结合双讲录音判断效果。

ESP-SR 固定增益接口只接受整数 dB，因此上行使用 10 dB 配合输入衰减 `31013/32768`，合成约 9.52 dB。输入先衰减，不会在送入限幅器前因乘法溢出；大声仍由原有限幅器保护，不能要求触顶信号也放大 1.5 倍。此调整不改变 ES8311 的 30 dB 模拟增益、AEC、唤醒输入、扬声器或协议格式，也不能提高原始拾音的信噪比。

`TX level` 记录上行增益前后的均方根幅度、峰值、接近满量程样本数和增益处理最长耗时。每 50 个成功处理的包发布快照，沿用播放诊断的 10 秒正常日志周期；`age` 表示快照新鲜度，`n` 不等于网络发送成功数。两个统计对象共 64 bytes 放在 PSRAM，采样本身不增加任务、PCM 缓冲或逐帧日志。

代码：[采集与发送](../components/starter_media/src/starter_media.c)、[AEC](../components/starter_media/src/starter_aec.c)、[通道定义](../components/starter_media/src/starter_aec.h)、[高通](../components/starter_media/src/p4_capture_highpass.c)。

## 音频播放

```text
TiRTC 音频回调
    -> 编码帧接收槽，记录到包时间和会话代次
    -> board_audio_rx 解码为 8 kHz 单声道 PCM
    -> 归还接收槽 -> PSRAM PCM 环形缓冲
    -> 按目标水位起播，每块最多 15 ms，由 I2S 推进供音
    -> 小幅重采样变速 -> FIR 8→16 kHz 重采样
    -> 16 kHz 双声道 I2S -> 扬声器
```

解码后先归还接收槽，避免 I2S 等待占住网络接收空间。物理容量固定：

| 缓冲 | 容量 |
| --- | --- |
| 编码帧接收槽 | 32 个，每槽 payload 最多 1500 bytes |
| PCM 环 | 8000 个 int16，即 16000 bytes |
| 包结束位图 | 1000 bytes |

结构字段、队列控制块和分配开销另算。自适应调整的是“积累多少音频再播放”，不反复申请或释放队列。

| 场景 | 策略 | 初始目标 | 调整范围 |
| --- | --- | --- | --- |
| H5 / 微信 | LOW_LATENCY | 20 ms | 20–100 ms |
| 设备呼叫 / 多人对讲 | ADAPTIVE_CALL | 120 ms | 120–560 ms |
| AI 对讲 | JITTER_SAFE | 120 ms | 120–320 ms |

控制器根据媒体时间戳和到包间隔估计抖动，同时记录软件空队列、恢复突发和本地写入压力。接近欠载时可减速 1.2%，积压时可加速 1.2% 或 2.5%；重采样相位跨块连续，不改变 I2S 时钟。这是小幅重采样，不是保持音高的时间伸缩。

变速水位包括软件 PCM 和 DMA 待播量估计；后者按成功写入量与经过时间更新，上限 90 ms，不是硬件读数。稳态变速目标至少为 120 ms，避免低延迟场景用 20 ms 起播门槛去要求一个 90 ms DMA 始终排空。此下限不改变表中的起播门槛和网络抖动目标。

连续供音由 `esp_codec_dev_write` / I2S 的可写空间推进，不再额外等待一个软件 20 ms 截止时间。当前 DMA 明确保持 6×240 帧，16 kHz 下每块 15 ms；在接近空载时，IDF 会放弃已经老化的半填充 DMA 块，即使 write 返回成功也可能留下零值空洞。网络播放每块输出对齐为 120 个 8 kHz 采样，升采样后恰好填满一个 DMA 块；写后只让出一个调度 tick，避免两套节拍叠加。仅改变本地出队粒度，网络包与采集上传的 20 ms 包保持不变；不修改 I2S 时钟、DMA 容量、Codec、AEC 或协议。

不足起播门槛的孤立短语，120 ms 没有新包后允许起播。连续播放剩下不足一块时，先等一个到包周期加一个本地播放块；若 DMA 待播量估计已不超过两块，提前续上剩余采样，不机械等到声卡排空后再补尾音。等待最长仍为 120 ms，不补造语音、不丢弃剩余采样。I2S 写入失败可能已输出部分数据，因此记录错误但不重播同块。流号变化只重置到包估计；新会话按代次隔离旧数据。应用按 SDK 交付顺序消费，不负责网络重传。

首次播放、确认停播后恢复及写入失败后的下一块，使用 5 ms 短渐入，并重置 8→16 kHz 插值历史，避免从静音前的旧采样跳入新音频。软件队列暂空时，保留历史到最后一次成功写入至少一块时间（15 ms）且待播量估计不超过一块，再补出 FIR 尾部；不能机械等到 120 ms 后才追加尾部，使短尾音与正文断开。新包及时到达则继续，不逐包渐入。等待输出锁时不消耗 PCM 或渐入进度。缓冲容量、变速比例和扬声器音量保持不变。这只处理恢复处的电平突变，不代替对底噪、回声和功放失真的真机排查。

表中数值是本地缓冲目标。端到端延时还包含网络、编解码、服务端和对端播放时间。

### 播放重采样

8→16 kHz 转换使用本工程依赖的 ESP-DSP `dsps_firmr_f32_ansi`，替换相邻采样取平均。滤波器为 63 抽头 Blackman 窗半带 FIR，末尾补零满足两个等长相位；每个相位的直流增益为 1，群延迟 1.9375 ms。它减少升采样镜像、保留原有语音频段，不产生原始 8 kHz 音频没有的高频内容，不是降噪器或音量放大器。

- 实时播放和提示音各自保存 FIR 历史，普通包边界不重置；新会话、欠载后恢复和写入失败后的重启才重置。两者继续共用输出互斥量，不允许提示音覆盖实时播放的工作缓冲。
- 自然结束后补出一次滤波尾部：62 个 16 kHz 单声道采样，约 3.875 ms。它不计为收到的新包；取消、静音、挂断或失效会话不继续播放旧尾音。提示音正常结束也排空，取消则立即放弃尾部。
- 重建峰值超出 int16 表示范围时饱和并计数，不能整数回绕。没有额外的压缩、门限静音或全局音量衰减。
- 两个转换器及工作数组均为静态 PSRAM，不新增任务、堆分配或内部 PCM 缓冲。最多每次转换 32 个输入采样，复用现有 I2S 输出数组；采集、AEC、唤醒、上传增益、协议格式、自适应水位和变速比例不变。

`test_playback_resampler.py` 使用实际 ESP-DSP 源码验证频响、镜像、跨包一致性、尾音和峰值边界；`test_prompt_resampler.py` 验证提示音的取消与排空。这些是数字信号与流程证据，不代表扬声器、功放或全双工听感已经验收。

### 诊断不阻塞供音

播放任务按 DMA 节拍供音，只更新控制器并非阻塞投递统计快照，不执行周期性串口打印。`audio_diag` 任务以优先级 2 输出 `AP flow`、`AP gen`、`AP level`、`TX level` 和 `CP` 日志；其 4096 bytes 栈和单槽快照存储放在 PSRAM，RTOS 控制结构留在内部 RAM。未新增 PCM 缓冲，也未改变采集、AEC、音量和变速比例。

日志拥塞时保留尚未报告的统计区间和错误计数，不等待、不覆盖未读快照。`at` 是快照时间，`diag_age` 是输出时快照的年龄，`pubmax` 是播放任务投递统计的最长耗时，`stack` 是日志任务栈的历史最小空闲字节数。正常仍每 10 秒记录一次，新丢弃或写入错误时缩短为 1 秒。

`empty` 表示软件缓冲为空且进入尾部排空阶段；语音自然结束也会增加，单凭它不能认定网络丢包。`dma_est` 是待播毫秒数估计；`late` 表示非重新起播的供音超过估计排空时刻 20 ms，并非硬件欠载计数。应一起检查 `rx/used/out`、到包间隔、I2S 写入错误与实际听感。

`AP level` 的三列依次为接收并入 PCM 队列、成功写入前的变速 PCM、成功写入的 16 kHz PCM。`n` 是采样数（8/8/16 kHz），`peak` 是绝对峰值，`rail` 是绝对值至少 32000 的采样数，`step` 是相邻采样最大跳变量，`max` 是测量最长耗时。`rail` 和 `step` 只提供线索：原始高频信号也可能跳变大，不能据此直接判定爆音。三组统计在 PSRAM，由 PCM 所有者更新；不采样录音、不新增任务，不把日志放回实时写入链路。

`test_i2s_playback_cadence.py` 使用本机 ESP-IDF 的实际写入函数，模拟 DMA 清零、轮转和调度停顿，验证成功写入与输出连续性是两件不同的事。它不替代 P4 真机的扬声器、电源、功放和持续播放回归；超过硬件缓冲能力的停顿仍会留下真实缺口。

`srcmax` 是本区间播放 FIR 转换的最长耗时，`srcclip` 是量化到 int16 时饱和的单声道采样数，`tail16` 是单独排出的 16 kHz 滤波尾部采样数；普通 `out` 仍按变速后的 8 kHz 等效采样计数。检查三项时不要把不同采样率或滤波尾部混算成网络重复包。转换耗时须结合真机 `late` 和 AEC 截止时间检查，不能用主机执行速度推断 MCU 余量。

代码：[PCM 容量](../components/starter_media/src/p4_audio_playout.h)、[消费逻辑](../components/starter_media/src/p4_audio_playout.c)、[自适应控制器](../components/starter_media/src/audio_playout_controller.c)。

## 视频

AI 和纯语音会话不启动摄像头；设备/微信视频按会话类型启动，H5 按查看流程启动。麦克风、摄像头和远端播放分别控制。关摄像头时先停发，再由视频任务停止硬件。

| 场景 | 设备上行 | 设备下行 |
| --- | --- | --- |
| H5 / 微信 | OV5647 1280×960，经 PPA 逆时针旋转 90°，输出 H264 960×1280、15 fps，目标 2 Mbps | H5 H264、微信 MJPEG，均顺时针旋转 90° 显示 |
| 设备视频呼叫 | H264 384×256、12 fps，目标 256 kbps | 受限 baseline H264，呈现尺寸 480×320 |

视频回调只复制和排队，后续分别解析、解码、转换、显示。入站池为 4×256 KiB PSRAM，显示画布为 480×320×2 = 307200 bytes；编解码帧池另算。

P4 的 TiRTC 发送缓存上限设为 2 MiB，配置在 `main/xiaotai_main.c`；这是容量上限，不等于实时占用量。

SDK 码率回调提交目标，由视频模块执行。实际码率、帧率和反馈是否生效需要运行时测量，不能由目标值推断。

代码：[视频任务](../components/p4_hardware/p4_video.c)、[媒体参数](../main/media/media_tuning.h)、[视频呈现](../main/services/call_video_renderer.c)。

## 内存与时序

| 资源 | 当前分配 |
| --- | --- |
| 采集、播放、发送任务栈 | 各 6144 bytes，PSRAM |
| p4_video_owner 栈 | 8192 bytes，PSRAM |
| 铃声/提示音任务 | 8192-byte 静态 PSRAM 栈，340-byte 内部 TCB；启动创建后常驻 |
| 热点 DNS、配网页 HTTP 任务 | 各 8192-byte 动态 PSRAM 栈，仅在热点配网期间存在 |
| Wi-Fi 信号/重启任务 | 3072-byte 内部栈；同时执行配网保存后的重启，不迁入 PSRAM |
| 业务会话、唤醒、HTTP 请求任务 | 分别为 24576、12288、13312-byte PSRAM 栈，创建后复用 |
| 微信 WHIP 建连任务 | 24576-byte PSRAM 栈，按建连创建；完成后通过 `vTaskDeleteWithCaps` 回收 |
| 启动任务 | 13312-byte 内部栈，完成绑定和 SDK 启动后退出；不作为稳态常驻开销 |
| AEC 工作帧、算法、音频帧池、预录、PCM 环、视频帧 | PSRAM |
| AEC 的 I2S 读取目标 | 对齐的内部 RAM 缓冲 |
| DMA 描述符、驱动必需内存、队列/TCB、关缓存路径 | 保留内部 RAM 要求 |
| esp-mqtt 自建任务 | 6144-byte 内部栈；当前客户端接口没有任务栈 caps 配置项 |
| I2S DMA | 90 ms 容量 |

PSRAM 用于较大的工作区，内部 RAM 留给驱动和实时约束。优化前区分总空闲内存、最大连续块和任务栈水位。DMA 容量只吸收短时波动，处理速度仍需跟上采样。

分配方式按生命周期选择：NVS 槽和铃声栈为编译期静态存储；媒体、模型和 HTTP 请求池在启动阶段一次申请后复用；HTTP 临时响应和配网服务按需申请、由所属模块回收。音频收发队列只传槽索引，不在每帧路径反复申请大块内存。将所有缓存都改成静态常驻会挤占闲置场景的可用空间。

PSRAM 栈与内部 TCB 分开分配。`WithCaps` 任务仍须用匹配的删除接口：热点 DNS 先关闭自己的 socket，再由配网生命周期调用者回收任务；停止超时保留句柄，不能直接释放正在运行的栈。IDF 的 `vTaskDeleteWithCaps(NULL)` 会临时创建内部清理任务，不能将它当成完全不占内部 RAM 的操作。

`sdkconfig.defaults` 的 192 KiB 内部预留是限制普通 `malloc` 使用的堆池，不是额外丢失的 192 KiB。通用 `malloc`、LVGL/cJSON 和 SDK 内部小对象仍受分配器策略影响；“优先 PSRAM”不等于“强制 PSRAM”。上述表格记录显式分配与已核对的客户端任务，不代表第三方库每个动态对象的实时位置。

C6 关闭 modem sleep 并回读检查。SDIO 使用 4 线 40 MHz SDR；当前驱动不能把 50 MHz 当作同模式加速选项。RPC 按请求 UID 和响应类型匹配，初始化失败由所属模块回收资源，详见 [Hosted 修正](../components/espressif__esp_hosted/LOCAL_CHANGES.md)。

## 手机热点配网

页面由 `wifi_manager/web/setup.html` 内嵌提供，不需要文件系统、CDN 或互联网。HTTP 仍只接受从 AP 接口到达的连接；POST 同时检查浏览器 Origin。扫描、保存与重启的失败分别返回，不把“配置已保存”显示成“已经联网”。

- `POST /api/scan` 只投递扫描意图；默认事件循环执行非阻塞扫描并消费 SCAN_DONE。连接尝试进行中不抢占扫描，扫描进行中暂缓已有重连定时器的 connect；扫描完成后恢复原重连计划。
- 结果最多取 24 个 AP，同名 SSID 保留较强信号。取回、失败和取消路径释放驱动列表；10 秒仍未完成则停止扫描，等待该次 DONE 后才接受下一次扫描。
- `GET /api/networks` 读取缓存，返回名称、信号、认证支持和“已保存”标记，不返回密码。未知认证方式只展示，不提供错误的密码连接入口。
- `wifi_cfg/credentials` 仍为原 99-byte 当前配置；新增 `wifi_cfg/known` 为 394-byte 版本化记录，只保存最近成功获得 IP 的 4 个网络。原配置无需迁移；升级后首次成功联网会建立历史。失败的配网提交不加入历史。
- 成功事件通知既有 Wi-Fi 信号任务，由它经公共 NVS worker 更新历史。重复连接同一配置不反复写 Flash；清除 Wi-Fi 配置同时清除历史，并阻止迟到通知恢复已删除的凭据。
- 选择已保存网络提交 `ssid + use_saved`，设备端查找密码；修改密码时提交 `ssid + password`。保存成功仍重启联网。历史缺失、损坏或保存失败保持可见，不伪造自动填充成功。

没有新增任务栈。扫描缓存 876 bytes、本次启动凭据 98 bytes 位于 PSRAM；历史写入临时记录、驱动结果数组和 12 KiB JSON 输出缓冲也显式申请 PSRAM，HTTP 栈继续为 8192 bytes。内部 RAM 仅新增控制状态与互斥量等小对象。JSON 按单个网络逐条序列化，小型 cJSON 节点仍遵循系统分配策略，不常驻完整列表。上述静态缓存位置已从 1.1.2 链接结果核对，运行时峰值和栈水位需上板测量。

配网热点仍无密码、网页仍为本地 HTTP；自动复用不会向手机返回旧密码，但无法消除开放热点上提交新密码的旁听风险。更改热点安全策略需单独确认。

修改后的验证顺序见[测试与排障](TESTING.md)。
