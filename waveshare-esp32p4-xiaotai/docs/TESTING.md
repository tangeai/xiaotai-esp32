# P4 排障与验证

先确认声音或画面停在哪一段，再决定改哪里。设备绑定、RTC 连接、音频到包和视频首帧各有自己的日志；一个“已连接”解释不了后面的黑屏。记录板型、芯片修订、固件与 SDK 版本后，从最早出现异常的位置开始查。

## 按阶段排查

| 现象 | 先检查 |
| --- | --- |
| 构建缺文件 | ESP-IDF 5.5.4、esp32p4 目标、依赖锁，以及同级 S3 和 `common/` |
| 启动失败或重启 | 芯片修订、应用版本、panic/assert、内部 RAM 与 PSRAM |
| C6 未就绪 | 主从版本、供电、接线和 SDIO 日志；本版为 4 线 40 MHz SDR |
| Wi-Fi 连上但未上线 | IP、时间、服务发现响应，再查 MQTT |
| 绑定没有完成 | 临时 MQTT 订阅是否成功、六位码是否有效、绑定确认与身份代次 |
| 联系人可见，呼叫失败 | 授权、平台请求结果、TiRTC 连接回调和错误码，区分业务与 RTC 阶段 |
| 通话接通，对方听不到 | 麦克风、AEC 输出、G.711 A-law 编码、发送计数和对端订阅 |
| 收到包，本机没有声音 | 接收格式、解码、PCM 水位、I2S 提交，再检查扬声器与听感 |
| 有采集但对端没有画面 | 会话是否启用视频、编码输出、发送帧格式、关键帧和对端订阅 |
| 收到视频但本机黑屏 | 帧格式与尺寸、解码错误、显示队列和呈现计数；设备下行 H.264 与微信下行 MJPEG 分开查 |
| 切换后卡住或内存不回落 | 退出前后状态、任务栈、最大连续内部块及队列；区分常驻池与泄漏 |

## 改完以后，试这几项

先打通电话，再检查这些容易被“一次成功”漏掉的情况：

- **声音与画面**：轮流讲话、同时讲话，听底噪和断续；移动物体，观察方向、裁切与连续画面。
- **挂断与重拨**：双方轮流做主叫，试接听、拒绝、挂断和再次呼叫；检查退出后的队列、任务和内存。
- **对端与网络**：设备、微信、H5 分别验证涉及的路径，再测弱网和断网恢复。
- **其他使用入口**：修改共用媒体代码后，也试 AI 进入/退出、触摸及长时间运行。

`tools/` 中的主机检查适合先查代码问题，按脚本准备 Python、gcc/g++ 或 Bash。实际画面、声音和恢复过程仍要看目标板。提问题时附上首次异常前后的日志，并去掉凭据与个人信息。

## 网络与凭据

所附 P4 SDK 的 RTC 连接使用 HTTPS 并验证证书。应用 API、MQTT 则按服务发现配置连接，需要另外检查：RTC 做了认证，并不覆盖这两条路径。部署前核对[版本与依赖](../VERSION.md)中的说明。
