# S3 排障与安全说明

先确认声音停在哪一段，再决定改哪里。设备“已绑定”说明身份就绪，“已连接”说明 RTC 连通；真正听到声音，还要经过收包、解码和播放。记录板型、固件与 SDK 版本后，从最早出现异常的位置开始查。

## 按阶段排查

| 现象 | 先检查什么 |
| --- | --- |
| 构建缺文件 | ESP-IDF 5.5.4、esp32s3 目标、依赖锁和根 `common/` 模型原件 |
| 连上 Wi-Fi，设备仍未上线 | IP、系统时间、服务发现、MQTT 和 SDK started 日志 |
| 联系人可见，呼叫失败 | 联系人授权、平台请求结果、连接回调与错误码，分清业务失败和 RTC 失败 |
| 通话接通，对方听不到 | 麦克风采集、AFE 输出、G.711 A-law 编码、发送计数与对端订阅 |
| 收到包，本机没有声音 | 接收格式、解码、队列水位、I2S 提交和扬声器，按此顺序检查 |
| 声音断续或挂断后仍有声音 | 到包间隔、缓冲水位、会话代次与退出日志；先保存日志，保留出错现场 |

需要串口诊断时启用 `CONFIG_XIAOTAI_DEVELOPMENT_CONSOLE`，使用 `version`、`status`、`voice-diag`；默认关闭。主动断开 Wi-Fi 会回到热点配网，临时掉线则重连已保存的网络。

## 改完以后，试这几项

先打通电话，再试接听、拒绝、挂断、重复呼叫和断网恢复。改到了哪条链路，就用对应的设备、微信或 H5 对端试一次。听双讲、底噪和断续时，让真人开口：数据包计数很好看，也可能听着不舒服。

`tools/` 中的 Python 检查和主机测试适合先查代码问题，部分脚本需 Bash、gcc/g++。实际声音和长时间运行表现，留给目标板检查。

## 网络与凭据

**当前连接方案仅适合受控网络评估。** 默认服务发现使用 HTTP，所附 S3 TiRTC 2.3.0 SDK 的 HTTPS 链路未验证服务端证书，令牌、设备凭据和控制消息存在被窃听或篡改的风险。ESP-IDF 证书包不覆盖这条 SDK 链路。

用于生产环境前，需要补齐协议与 SDK 的服务端认证，并实测两种情况：有效证书能连接，无效证书被拒绝。

## 已知限制

- 绑定提示音下载期间，取消要等下载返回。遇到等待时先记录下载阶段和响应，保留设备身份便于复现。
- 下行池容量固定；长时间不到包、溢出或编码格式不符会造成等待或丢弃。最大 500 ms 预缓冲不能补回任意丢包。
- 微幅调速使用插值，不保证音高不变。唤醒距离、语音清晰度和双讲效果需真人验证。
